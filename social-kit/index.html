Post 2: From advisory to detection
How does a threat advisory become something useful to a security team?

Start with six questions:
1. Does the reported behaviour apply to our environment?
2. Which assets or identities could be affected?
3. What telemetry would show the behaviour?
4. Is that telemetry available and usable?
5. How will we test the detection?
6. What should an analyst do when it triggers?

MITRE ATT&CK provides a common reference for adversary tactics and techniques. The engineering work is connecting that reference to your own data, tests and response process.

Reference: https://attack.mitre.org/

Post 3: A useful project brief
Planning a SIEM, SOAR or EDR project?

A useful starting brief covers:
• The operational problem your team wants to solve.
• The platforms and data sources involved.
• What is in scope and what is outside it.
• The tests that will demonstrate completion.
• The documentation and handover your team needs.

For example, “improve alert quality” needs more definition before it becomes an engineering task. Which alerts? What is the current problem? How will the team assess the change?

Post 4: Before trusting a SIEM data source
Before relying on a new SIEM data source, ask five questions:

1. Are the expected events arriving?
2. Are timestamps and important fields usable?
3. Can the team identify delays or collection failures?
4. Do the intended detections work against representative test data?
5. Who owns investigation and repair when the source stops reporting?

For Microsoft Sentinel, analytics-rule health and audit information can help check rule execution and changes. Use it alongside checks of the underlying data.

Microsoft documentation:
https://learn.microsoft.com/en-us/azure/sentinel/monitor-analytics-rule-integrity

Post 5: Test the SOAR failure path
Before putting a SOAR workflow into production, review what happens when something goes wrong.

What if an enrichment service times out?
What if a required field is missing?
What if the workflow lacks permission?
Who receives the failure notification?
Which actions need approval?
How can the team inspect what happened?

Microsoft Sentinel provides automation health monitoring for automation rules and playbooks, including execution logs.

Documentation:
https://learn.microsoft.com/en-us/azure/sentinel/monitor-automation-health

A practical automation brief should include the success path, failure handling, ownership and acceptance tests.

Post 6: Review EDR coverage
An EDR deployment review should ask more than how many endpoints received an installation package.

Compare the expected device population with the security platform’s inventory. Then examine onboarding status, sensor health, reporting activity and any exceptions that need investigation.

In Microsoft Defender for Endpoint, the device inventory distinguishes onboarding status and sensor health. Those signals help frame the review; the team still needs to reconcile them with its expected assets.

Microsoft documentation:
https://learn.microsoft.com/defender-endpoint/devices-overview

Post 7: Give threat intelligence a job
Before adding another threat intelligence feed, define the decision it should support.

Are you trying to prioritise an investigation?
Review exposure to a reported campaign?
Develop a detection?
Enrich an existing alert?

For each use case, identify the relevant source, the evidence your team needs, the action it could change and the person responsible.

Then test the workflow with a small, representative example. That gives the team something concrete to evaluate before expanding the integration.
