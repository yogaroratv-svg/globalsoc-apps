After the Password Works: SSH Bots That Test Your Shell, Size Your GPU and Hunt for SMS Modems

Our SSH honeypot accepted any password for 40 decoy accounts. 3,412 logins later, the bots showed exactly what they do first: a six-test anti-honeypot kit tagged with random 32-hex tokens, GPU and miner sizing aimed at Solana-style accounts, and an SMS-modem and Telegram-session hunting kit. Every command, how the kits were attributed, and tested MDE + Sentinel and Splunk + CrowdStrike detections.

Key Sections: Where the Data Came From · Playbook 1: Is This a Honeypot? · Playbook 2: Is It Worth Mining? · Playbook 3: SMS Modems and Telegram · Playbook 4: Plant a Key · Kill Chain · Pyramid of Pain · Detections · When It Fires · IOCs

Data window: 29 October – 11 November 2026, the same Cisco ASA honeypot as the SSH tunnel post. Part of my honeypot detection series. Org A runs Microsoft Defender for Endpoint with Microsoft Sentinel; queries marked Tested ran against this honeypot's MDE data. Org B runs Splunk with CrowdStrike Falcon (Event Search field names); its queries were not run against this data.

1. Where the Data Came From

PAM on the honeypot accepted any password for 40 decoy accounts (admin, ubuntu, user, deploy, test, postgres, sol, validator, tradingbot and so on), and the login shell for each was a Python fake shell. That produced 3,412 successful logins (3,402 password, 10 keyboard-interactive/pam). Three sources recorded what happened next:

SourceWhat it capturedGap
Fake-shell log (ssh_post_auth_commands.jsonl)2,103 interactive commands from 9 IPs, all as adminThe file was created by the first session and, on the disk image, is owned by uid 1037 (admin) with mode 0644 (-rw-r--r-- 1 1037 nogroup). Every later session runs as its own user, so no other account could append. It also only logged interactive input, not exec requests.
MDE DeviceProcessEventsAbout 1,300 exec-mode commands (ssh user@host "cmd") across 31 accounts, as the argument of cisco-fake-shell -c "<cmd>"Interactive lines typed into the fake shell are stdin, not processes, so MDE can't see them.
auth.log + MDE DeviceLogonEventsEvery login: account, source IP, time, session lengthNo commands.

The two command sources are complementary: the honeypot log has the interactive anti-honeypot kit, MDE has the exec-mode recon. Neither alone shows the whole picture. Exec commands were attributed to a source IP by matching each one to the same account's SSH logon in the preceding 15 seconds (848 of 1,298 process records matched; scripted bots run their first command within a second or two). Treat those attributions as strong correlation, not proof.

Session length tells you these are scripts: of the accepted logins with a clean start and end, 1,906 lasted 1–5 seconds, 1,391 lasted 5–20 seconds, and only 16 lasted more than a minute.

2. Playbook 1: "Is this a honeypot?"

Nine IPs (2.57.122[.]150, 2.57.122[.]209, 2.57.122[.]76, 2.57.122[.]168, 195.178.110[.]228, 80.94.92[.]55, 80.94.92[.]234, 92.118.39[.]77, 92.118.39[.]49) logged in as admin, opened an interactive shell, and sent the six tests twice, each block under its own token, followed by a transport marker: 13 lines in 2.3 milliseconds. This is the first block of the first session from 195.178.110[.]228 (22:00:01 UTC, 29 October) plus the closing marker; the second block is identical except for its token (check_677f3ee5d8c6657e3c44dc5ed3dbd6f1):

sh -c 'printf '"'"'\n%s|%s\n'"'"' '"'"'check_feb6f67c69351db213e7c455636034cf_small_control'"'"' '"'"'check_feb6f67c69351db213e7c455636034cf'"'"''
sh -c 'printf '"'"'\n%s|%s\n'"'"' '"'"'check_feb6f67c69351db213e7c455636034cf_small_math'"'"' "$((402*668+23))"'
sh -c 'printf '"'"'\n%s|%s\n'"'"' '"'"'check_feb6f67c69351db213e7c455636034cf_small_pid'"'"' "$$"'
sh -c 'set -- '"'"'check_feb6f67c69351db213e7c455636034cf_arg1'"'"' '"'"'check_feb6f67c69351db213e7c455636034cf_arg2'"'"'; printf '"'"'\n%s|%s\n'"'"' '"'"'check_feb6f67c69351db213e7c455636034cf_small_positional'"'"' "$#|$1|$2"'
sh -c 'f_check_feb6f67c69351db213e7c455636034cf() { printf '"'"'\n%s|%s\n'"'"' '"'"'check_feb6f67c69351db213e7c455636034cf_small_function'"'"' "$1|$#"; }; f_check_feb6f67c69351db213e7c455636034cf '"'"'check_feb6f67c69351db213e7c455636034cf_function_value'"'"''
sh -c 'printf '"'"'\n%s\n'"'"' '"'"'check_feb6f67c69351db213e7c455636034cf_small_done'"'"''
echo; echo 'check_700847ec050075ea73e058d3713539db_transport_done'

What each test proves, and what a real /bin/sh prints:

TestConstructReal shell outputWhat it defeats
small_controlPlain printf of the tokencheck_…_small_control|check_…Baseline: is output reflected at all, and is '"'"' quote nesting parsed?
small_math$((402*668+23)) with random operands268559Canned-response honeypots. The answer changes every session, so a lookup table can't pass.
small_pid"$$"A plausible PIDShells that don't expand special parameters.
small_positionalset -- a b; "$#|$1|$2"2|…_arg1|…_arg2Emulators that can't hold shell state across a statement.
small_functionDefine and call a function…_function_value|1Pattern-matching shells (Cowrie-style command tables) without a real parser.
small_done / transport_doneTerminator markersThe markerTells the client the channel delivered every line, so a missing answer is the shell's fault, not the network's.

Every token is a fresh 32-hex value per session, and each bot reconnected about every two minutes with a new token (22:00:01, 22:02:15, 22:04:16, 22:06:32 for 195.178.110[.]228). Echoing the token doesn't help a honeypot: the test is whether the computation around the token is right. My fake shell had canned answers for a handful of commands (echo, id, whoami, uname, pwd, ls, show version, /proc/cpuinfo, /proc/mounts), but every test arrived wrapped in sh -c '...', which it doesn't parse. It answered only the bare echo; echo '…_transport_done' line, so it failed all six tests in every session. None of these nine IPs ever sent a download command. The kit is a gate: fail it and the bot moves on, which is why a low-interaction SSH honeypot collects passwords but very few payloads.

3. Playbook 2: "Is it worth mining?"

About 630 GPU-probe commands across accounts named for crypto infrastructure (sol, validator, trading, tradingbot) as well as generic ones (ubuntu, docker, ftp, teamspeak, oracle, centos). Each session ran the same fixed set, one SSH exec per command:

uname -s -v -n -r -m
uname -m | awk '{printf $1}'
uptime -p
lspci | grep VGA | cut -f5- -d ' '
lspci | grep VGA -c
lspci | grep "3D controller" | cut -f5- -d ' '
nvidia-smi -q | grep "Product Name" | head -n 1 | awk '{print $4, $5, $6, $7, $8, $9, $10, $11}'
nvidia-smi -q | grep "Product Name" | awk '{print $4, $5, $6, $7, $8, $9, $10, $11}' | grep . -c

Counts across the whole window, one per SSH exec (unique process IDs): uname -s -v -n -r -m 333, uname -m | awk… 299, lspci … VGA … cut 116, uptime -p 107, lspci | grep VGA -c 102, lspci "3D controller" 101, both nvidia-smi lines 102 each. (The fake shell starts with #!/usr/bin/env python3, so MDE often logs each exec twice under the same PID, once as env and once as python3.10. Count PIDs, not rows.) "3D controller" is how datacentre GPUs (NVIDIA A100/H100 class) enumerate on PCI, as opposed to "VGA" for consumer cards, and the second nvidia-smi line counts the GPUs. uptime -p answers "is this a short-lived sandbox?". The kit is sizing the host for GPU mining or for resale as GPU compute. The account names show the target list was built for Solana validators and trading bots, the servers most likely to have both GPUs and wallets.

Time-correlated sources (logon of the same account within 15 s): 103.159.2[.]113 125 commands, 179.43.153[.]18 110, 2.57.122[.]238 82, 195.178.110[.]26 80, 209.99.190[.]186 26. A shorter variant (nproc, uname -m, lspci | egrep VGA && lspci | grep 3D) ran 20 times each in 102 seconds (03:09:40–03:11:22 UTC) on 3 November across oracle, mysql, git, pi, jenkins, zabbix and others, from 79.175.176[.]177.

The plain uname probes came mostly from the brute-force workers themselves: 109.160.32[.]105, .160, .200, .37, .40, .104 and 77.239.124[.]34, .35, .38, .148. That is the guesser confirming a hit with one harmless command before it reports the credential upstream.

4. Playbook 3: SMS modems and Telegram sessions

A separate kit: five sessions as admin and test between 2 and 11 November, eight commands per session, 40 in total (the 2 November session time-correlates to 191.180.161[.]164). One ls lists every location that matters for SMS fraud or account takeover:

ls -la ~/.local/share/TelegramDesktop/tdata /home/*/.local/share/TelegramDesktop/tdata /dev/ttyGSM* /dev/ttyUSB-mod* /var/spool/sms/* /var/log/smsd.log /etc/smsd.conf* /usr/bin/qmuxd /var/qmux_connect_socket /etc/config/simman /dev/modem* /var/config/sms/*
PathWhy an attacker wants it
TelegramDesktop/tdataTelegram Desktop's session store. Copying it hijacks the logged-in Telegram account without a password or 2FA code.
/dev/ttyGSM*, /dev/ttyUSB-mod*, /dev/modem*GSM/LTE modem serial devices: send SMS, read inbound OTP codes.
/var/spool/sms/*, /etc/smsd.conf*, /var/log/smsd.logsmstools3 SMS gateway spool, config and log: stored messages and the modem config.
/usr/bin/qmuxd, /var/qmux_connect_socketQualcomm QMI multiplexer used by cellular modules in routers and IoT gateways.
/etc/config/simman, /var/config/sms/*SIM-manager and SMS config on industrial cellular routers (OpenWrt-based).

The same sessions also ran ps | grep '[Mm]iner' and ps -ef | grep '[Mm]iner' (is a competitor already mining here?), locate D877F783D5D3EF8Cs (a fixed marker string, either a file a previous infection leaves or a deliberate canary), echo Hi | cat -n (a pipe test, the same idea as Playbook 1), ifconfig, uname -a and cat /proc/cpuinfo, once per session. (A separate echo SHELL_TEST probe ran five times on 7–8 November as admin, support and test, time-correlated to 35.187.231[.]181.) The kit wants three things from one login: a modem to monetise, a Telegram session to steal, and a CPU nobody else is mining on.

4b. Playbook 4: plant a key

Two identical execs on 11 November, at 14:10:36 and 19:59:35 UTC, both as ubuntu, tried to make the access permanent. MDE recorded the command verbatim (the **** is as logged):

uname -a && nproc && sh -c 'cd ~ && \
mkdir -p **** && \
chattr -i .ssh 2>/dev/null || true && \
cd .ssh && \
chattr -i authorized_keys 2>/dev/null || true && \
echo "ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC3crWsao+ctzbToLa7oSGyaldBFuTTRTFVk9A106sesz/d5UXOYJmXl9iDe2IX6FfEE+XQmEIJ0RS9DBrdmhR36a8uFGAI8x0FjB3FmAmaTg+BM6Yamhxepv+AS4mCwYtDUFjNmqAjFXZqraWmVGNGgdCDpcK8LpRDierLMZ98uIpsaFvqHixq0stTu+AyynD3JD4oF+eFxfn+Rvw2HtW0LTd0TEq+ZYdTG80/MVhvlgJ61L9PlsiAQWbVeps8cMA1Xj1UNMJ9JzlBRCcWYKn00RmEuwzzhMejX82gEnXuY5DL8VpZjI90a6lmuaqfqtbRsiG/rG0c8oTEgpEEPJ1z $(whoami)@$(hostname)" >> authorized_keys && \
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys'

Three details make it a good detection anchor. chattr -i on .ssh and authorized_keys removes the immutable flag a previous intruder may have set to lock others out. The key comment is generated on the victim ($(whoami)@$(hostname)), so the line looks like a normal user key in the file. And the uname -a && nproc prefix is the same sizing step as Playbook 2, fused into one exec. Key fingerprint: SHA256:sbTUqMHiIZ3gLrJKR2zACW5y9JdUKzEr0XzwF9tgR2I (MD5 fe:13:7c:98:d9:d1:b0:6a:71:3a:72:af:15:f0:da:da). The fake shell executed none of it.

7. Detections

D1. The anti-honeypot kit (T1497, T1059.004)

Org A Tested: 0 rows, and correctly so. The fake shell read these lines from stdin, so no process was created. On a real host each test is an sh -c process and this fires on the first session.

// A1: the anti-honeypot check kit (token check_<32 hex>_small_<test> or _transport_done)
DeviceProcessEvents
| where Timestamp > ago(30d)
| where ProcessCommandLine matches regex @"check_[0-9a-f]{32}_(small_(control|math|pid|positional|function|done)|transport_done|arg[12]|function_value)"
| summarize Commands = count(), Tests = make_set(extract(@"check_[0-9a-f]{32}_([a-z_0-9]+)", 1, ProcessCommandLine), 12),
            Tokens = dcount(extract(@"check_([0-9a-f]{32})", 1, ProcessCommandLine))
          by DeviceName, AccountName, bin(Timestamp, 10m)

Org B

`comment("B1: Falcon - anti-honeypot check kit tokens")`
event_simpleName=ProcessRollup2 event_platform=Lin
| regex CommandLine="check_[0-9a-f]{32}_(small_(control|math|pid|positional|function|done)|transport_done|arg[12]|function_value)"
| rex field=CommandLine "check_(?<token>[0-9a-f]{32})_(?<test>[a-z_0-9]+)"
| bin _time span=10m
| stats count as cmds values(test) as tests dc(token) as tokens by _time aid ComputerName UserName

The regex is narrow enough to run as a near-real-time rule. A real /bin/sh never produces this token format on its own.

D2. GPU and miner sizing burst (T1082, T1120)

Org A Tested: 108 one-minute windows across 15 accounts, 29 Oct 23:35 – 10 Nov 18:24 UTC. Every window had three or more distinct probes.

// A2: GPU / miner sizing burst after an SSH login
DeviceProcessEvents
| where Timestamp > ago(30d)
| where ProcessCommandLine has_any ("nvidia-smi", "lspci", "uptime -p", "nproc")
| extend Probe = case(ProcessCommandLine has "nvidia-smi", "nvidia-smi",
                      ProcessCommandLine has "3D controller", "lspci-3d",
                      ProcessCommandLine has "VGA", "lspci-vga",
                      ProcessCommandLine has "uptime -p", "uptime-p", "nproc")
| summarize Probes = dcount(Probe), ProbeSet = make_set(Probe), Cmds = count() by DeviceName, AccountName, bin(Timestamp, 1m)
| where Probes >= 3

Org B

`comment("B2: Falcon - GPU / miner sizing burst")`
event_simpleName=ProcessRollup2 event_platform=Lin (CommandLine="*nvidia-smi*" OR CommandLine="*lspci*" OR CommandLine="*uptime -p*" OR CommandLine="*nproc*")
| eval probe=case(like(CommandLine,"%nvidia-smi%"),"nvidia-smi", like(CommandLine,"%3D controller%"),"lspci-3d",
                  like(CommandLine,"%VGA%"),"lspci-vga", like(CommandLine,"%uptime -p%"),"uptime-p", true(),"nproc")
| bin _time span=1m
| stats dc(probe) as probes values(probe) as probe_set count by _time aid ComputerName UserName
| where probes>=3

On real GPU hosts, monitoring agents run nvidia-smi constantly. Exclude them by parent process (dcgm-exporter, nvidia-persistenced, your metrics agent) and keep the condition that lspci and uptime -p appear in the same minute.

D3. SMS-modem and Telegram-session hunting (T1005, T1120)

Org A Tested: 10 process records, accounts admin and test, 2–11 November (five sessions; MDE records both the env and the python3 process for each command, so expect two rows per command on hosts with interpreter wrappers).

// A3: SMS-modem / Telegram-session hunting kit
DeviceProcessEvents
| where Timestamp > ago(30d)
| where ProcessCommandLine has_any ("TelegramDesktop/tdata", "/dev/ttyGSM", "/dev/ttyUSB-mod", "/var/spool/sms",
                                    "smsd.conf", "smsd.log", "qmuxd", "qmux_connect_socket", "/etc/config/simman", "/dev/modem")
| project Timestamp, DeviceName, AccountName, ProcessCommandLine, InitiatingProcessCommandLine

Org B

`comment("B3: Falcon - SMS modem / Telegram session hunting")`
event_simpleName=ProcessRollup2 event_platform=Lin
  (CommandLine="*TelegramDesktop/tdata*" OR CommandLine="*/dev/ttyGSM*" OR CommandLine="*/var/spool/sms*"
   OR CommandLine="*smsd.conf*" OR CommandLine="*qmuxd*" OR CommandLine="*/etc/config/simman*" OR CommandLine="*/dev/modem*")
| table _time ComputerName UserName CommandLine ParentBaseFileName

Almost zero false positives on servers. On an actual SMS gateway, exclude the smstools daemon user.

D5. Seconds-long scripted sessions across many accounts

Org A (Sentinel Syslog; not run, because this honeypot's auth logs were not forwarded to Sentinel. The same shape is visible in the auth.log numbers in section 1.)

// A5 (Sentinel Syslog): logins that live for seconds - scripted check sessions, many accounts
Syslog
| where ProcessName == "sshd"
| extend Src = extract(@"Accepted \S+ for \S+ from (\S+)", 1, SyslogMessage),
         User = extract(@"Accepted \S+ for (\S+) from", 1, SyslogMessage)
| summarize Start = min(TimeGenerated), End = max(TimeGenerated), Src = take_anyif(Src, isnotempty(Src)), User = take_anyif(User, isnotempty(User))
          by Computer, ProcessID
| where isnotempty(Src)
| extend Secs = datetime_diff("second", End, Start)
| summarize Sessions = count(), ShortSessions = countif(Secs <= 20), Users = dcount(User) by Computer, Src, bin(Start, 1h)
| where ShortSessions >= 5

Org B

`comment("B4: Splunk linux_secure - seconds-long scripted SSH sessions across many accounts")`
index=linux sourcetype=linux_secure process=sshd
| rex "sshd\[(?<pid>\d+)\]"
| rex "Accepted \S+ for (?<user>\S+) from (?<src>\S+)"
| stats min(_time) as start max(_time) as end values(src) as src values(user) as user by host pid
| where isnotnull(src)
| eval secs=end-start
| bin start span=1h
| stats count as sessions sum(eval(if(secs<=20,1,0))) as short dc(user) as users by host src start
| where short>=5

D6. Key implant with chattr -i (T1098.004, T1222.002)

Org A Tested: 4 process records: the two 11 November attempts, each logged as env + python3.

// A6: authorized_keys append preceded by chattr -i (lock-breaking key implant)
DeviceProcessEvents
| where Timestamp > ago(30d)
| where ProcessCommandLine has "authorized_keys" and ProcessCommandLine has_any ("chattr -i", ">> authorized_keys", "ssh-rsa ", "ssh-ed25519 ")
| project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine

Org B

`comment("B6: Falcon - authorized_keys implant with chattr -i")`
event_simpleName=ProcessRollup2 event_platform=Lin CommandLine="*authorized_keys*" (CommandLine="*chattr -i*" OR CommandLine="*ssh-rsa *" OR CommandLine="*ssh-ed25519 *")
| table _time ComputerName UserName FileName CommandLine ParentBaseFileName

On a real host also watch the file itself: DeviceFileEvents / Falcon FileWritten for */.ssh/authorized_keys by anything other than your configuration-management agent.

8. When It Fires

  • D1 on a real server means a bot has a working login and is deciding whether to stay. Assume the next session drops a payload. Lock the account and kill its sessions now. Org A Live Response pkill -KILL -u <user>, then isolate if anything ran after the kit. Org B RTR kill the sessions, or network-contain.
  • D2 or D3: pull every command from the same account in the previous and next 10 minutes (DeviceProcessEvents / ProcessRollup2). Look for wget, curl, chmod +x, writes to /tmp, /dev/shm, ~/.ssh/authorized_keys.
  • D3 on a host that really has a modem or Telegram Desktop: treat the Telegram account as compromised (terminate all sessions from another device), and review SMS logs for OTP messages read in the window.
  • Whatever fired, find the password: every one of these logins needed one. Rotate it and turn off password authentication on the host.
