Router Botnets Knocking on a PHP Server: 137 IoT Exploits, Decoded

Our PHP honeypot is not a router, but 52 IP addresses tried more than 20 different router, camera and NAS exploits on it. We show the payloads in full: a 19-exploit loader with a four-stage beacon, an out-of-band scanner with a callback token per request, Mozi bots that are still spreading, and a Mozi payload hidden in a header that nginx never logged but our packet capture did.

Part of the PHP honeypot series. Data: nginx request log from vm-php-cve-lab, 22 October – 15 November 2026 (UTC; the VM was switched off from 9 to 15 November), plus a packet capture from 15–16 November. Payloads are shown as captured; URLs and domains are defanged.

1. Summary

137 requests from 52 IP addresses tried to exploit routers, cameras, DVRs, NAS boxes and firewalls on a server that is none of those things. Every one of them failed (400, 404, 405, or a connection the sender abandoned), because the paths do not exist on a PHP site. They are still worth reading, because they show how the botnets that do infect such devices work:

  • One loader fired the same 19 exploits in the same second, twice in one day. Its shell payload reports back at four points (started, downloaded, ran, failed) and names each victim by its hostname.
  • Another sender put a unique 24-character callback token in each of 37 exploits, so its server knows exactly which exploit worked on which target. That is how out-of-band vulnerability scanners work, legitimate or not.
  • Mozi, a peer-to-peer botnet whose operators were reported arrested in 2021, is still spreading. 15 Mozi requests came from 15 different infected devices, most of them offering the malware from their own built-in web server.
  • Two Mozi requests in our packet capture carry the command in the SOAPAction header. The body is harmless. nginx logs bodies, not that header, so in our logs the same exploit looks like a broken port-mapping request.
  • A TP-Link botnet node sends the same exploit every 46 hours, pointing victims at 0.0.0.0, an address that cannot serve them anything.

2. Why a PHP Server Gets Router Exploits

Botnets that infect devices do not check what they are talking to. They scan an address range for an open port 80, then send their whole exploit list to every address that answers. A request costs them nothing; checking costs time. So a cloud VM running a PHP site gets the same Hikvision, GPON and D-Link exploits as a home router.

Step by step:

  1. Check in. Request :8099/b/e/<hostname> from the server 77.239.124[.]167. $(uname -n) puts the device's hostname in the path, so the operator's web log becomes a list of devices where the exploit worked. Each step tries busybox wget, plain wget and curl, in that order, because IoT firmware ships with different subsets of the three.
  2. Find a writable directory. /tmp, or /dev/shm if that fails. Set a PATH that covers both normal Linux and Android (/system/bin, /system/xbin).
  3. Download the next stage to a hidden file .y from hxxp://77.239.124[.]167/s. If the file is empty, try a second address on port 23413 with a 16-character key in the path: /k/a56f1a4933ad0bca/s. The key probably lets the server tell this campaign's downloads apart or refuse anyone without it; we cannot confirm which.
  4. If the download worked: report /b/f/<hostname>, run .y with whichever shell exists, then report /b/r/<hostname>.
  5. If it did not: report /b/n/<hostname>.

Our reading of the letters is e for executed, f for fetched, r for ran, n for nothing. The operator gets a funnel per exploit and per device type, without a single line of code on the victim beyond this command. We did not request any of these URLs.

Two of the 19 exploits per run target PHP software (PHPUnit and ThinkPHP); both got 404 here. Their PHP side is covered in the legacy PHP RCE post.

The command does nothing on the target except fetch one URL: hxxp://178.83.188[.]141:8880/t/<token>, by any of three methods, with all output discarded. The token is different in every request: 37 distinct tokens across the 38 requests (each appears three times, once per download method), and the one request without a token is a bare GPON path. When a vulnerable device runs the command, the scanner's server receives a request for that token and knows which target and which exploit it belongs to. Nothing is installed.

That is out-of-band vulnerability detection, the same technique that commercial scanners and bug bounty tools use. We cannot tell from this traffic whether the operator is a researcher, a vendor or a botnet operator building a target list. The results would be equally useful to all three.

6. Mozi in a Header: the Packet Capture

The lab ran a rolling packet capture (tcpdump, full snap length, 20 files of 10 MB) on port 80 and the Docker bridges. A ring that small holds about a day and a half of traffic, and the last of it was overwritten on 15 November when the VM was restarted and a large package download passed through the capture filter. The packets for the requests from 22 October to 15 November no longer exist. What remains is the nginx request log (request line, User-Agent, Content-Type and the complete request body) and the Apache log from inside the container, both shipped to Microsoft Sentinel as they were written. Everything on this page except the packet capture in this section is from those two sources.

The new capture (15 Nov 09:06 – 16 Nov 00:10 UTC) caught 2 Mozi attempts against D-Link's HNAP interface. This is the first, complete:

The packets also explain the odd status. The header says Content-Length: 640, but the body is 535 bytes. nginx waits for the rest, and it never comes:

The request arrives one second in. Eleven seconds of silence follow; then the sender gives up and closes, and nginx closes too, without sending a response. nginx logs that as status 400 with 0 bytes sent, which is exactly what the three earlier records show. The missing bytes do not matter to the attacker, because the injection is in a header, not the body.

The gap between visits is 46.0 to 46.4 hours, every time. The exploit is the TP-Link Archer AX21 country-code injection (CVE-2023-1389), which botnets including Mirai variants have used since 2023. But the download address is 0.0.0.0. On Linux that means "this machine", so an infected router would try to download router.tplink.sh from its own web interface and get nothing. 10. What the Honeypot Answered

Status codes across all 137 requests: 400 x19, 404 x97, 405 x6, 499 x15. None of these paths exist on the honeypot. nginx passed the requests through; Apache inside the container answered the URL-borne commands that contain raw spaces with 400 (a malformed request line), the rest with 404, and the Hikvision PUT with 405. 499 means the client hung up before the answer came. No request in this post reached code that could run it, and the container's filesystem shows no downloaded file (the list is in the RedTail post).

So the risk is not to a server like ours. It is to the devices these exploits were written for, which sit on home and office networks with no logging at all.

12. Detection (KQL)

Shell download chains anywhere in the request line or body. This catches every loader in this post except the header-borne one:

Syslog
| where SyslogMessage startswith "php_http: "
| extend j = parse_json(substring(SyslogMessage, 10))
| extend Client = tostring(j.client), Req = tostring(j.request), Body = tostring(j.body), Status = toint(j.status), UA = tostring(j.user_agent)
| extend Text = url_decode(strcat(Req, " ", Body))
| where Text matches regex @"(?i)(wget|curl|tftp|busybox)(\s|\$\{IFS\}|\+|%20)" and Text has_any ("/tmp", "| sh", "|sh", ";sh", "chmod", "/dev/null")
| extend Server = extract(@"(?i)https?://([0-9a-z\.\-]+(:\d+)?)", 1, Text)
| summarize Requests = count(), Paths = make_set(extract(@"^\S+ (\S{1,60})", 1, Req), 25), Servers = make_set(Server, 10), FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated) by Client, UA
| order by Requests desc

For the header-borne HNAP exploit you need the header. If your proxy can log it, add $http_soapaction to the nginx log format and alert on backticks or $( in it. Without it, the closest proxy for the request is a POST /HNAP1/ with no User-Agent that ends in status 400:

Syslog
| where SyslogMessage startswith "php_http: "
| extend j = parse_json(substring(SyslogMessage, 10))
| where tostring(j.uri) startswith "/HNAP1" and tostring(j.method) == "POST" and isempty(tostring(j.user_agent))
| project TimeGenerated, Client = tostring(j.client), Status = toint(j.status), BytesIn = tolong(j.bytes_in), BytesOut = tolong(j.bytes_out)

And on the network side, any device on your network fetching a URL containing its own hostname, or a path like /t/ plus 24 hex characters, is reporting in to someone.

13. Mitigation

  • Do not expose device admin interfaces to the internet. Every exploit here needs the router, camera or NAS web UI to be reachable from outside. Turn off remote management and UPnP on the WAN side.
  • Replace end-of-life devices. Many targets here (Netgear DGN, Linksys E-series, Huawei HG532, MVPower and AVTECH DVRs, D-Link DNS-320) will never get a fix.
  • Change default and ISP maintenance passwords (admin, user, adminisp, ec8) or ask the ISP to disable those accounts.
  • Log request headers that carry payloads on anything internet-facing, at least SOAPAction, Cookie and Referer, or keep packet captures. Section 6 shows what a body-only log misses.
  • Block outbound traffic from IoT networks to anything but what the devices need. A camera that cannot reach 77.239.124[.]167 cannot download the next stage or report in.
  • On web servers, reject what is not yours. A WAF or proxy rule that returns 403 for /cgi-bin/, /goform/, /HNAP1, /GponForm/, /boaform/ and /SDK/ on a PHP site removes a lot of log noise. It does not add much protection, because these exploits cannot work there anyway.
