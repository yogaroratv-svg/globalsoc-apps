Our PHP Honeypot, 22 October to 15 November: 21,811 Requests, 131,113 SSH Logins, Every Attack Decoded

We exposed an unpatched PHP 8.3.35 server the day after PHP2Shell was disclosed and recorded everything that arrived. This is the overview and index of the series: who came, how fast, what they tried, and what we could and could not prove from the logs and packet captures.

Key Sections: Summary · The Setup · The Numbers · The Series · What We Learned · What We Could Not Prove · Data and Methods

Series overview. Data: nginx request log, container Apache log, SSH logs and packet captures from vm-php-cve-lab, 22 October – 15 November 2026 (UTC; the VM was switched off from 9 to 15 November).

1. Summary

On 21 October 2026 two PHP vulnerabilities, CVE-2026-109618 and CVE-2026-109619 ("PHP2Shell"), were disclosed. The next day we put an unpatched PHP 8.3.35 container on the internet, behind an nginx proxy that logs every request body, with SSH open on the same address. It was online for 17.9 days, then switched off, then briefly on again on 15 November.

  • 10,509 web requests came from 1,148 addresses in 55 countries. A single Qualys scan sent another 11,262 in 31 minutes.
  • The first stranger arrived 33 minutes after start-up. Real PHP2Shell traffic started 21 hours in, and a cryptominer gang had added PHP2Shell to its kit within two days.
  • Most traffic was not aimed at PHP2Shell. A third of all requests hunted for secrets (.env, .git, cloud keys). The rest tried exploits for PHPUnit, PHP-CGI, ThinkPHP, React2Shell, routers, cameras and VPNs, whether or not the server ran any of them.
  • SSH took 131,113 password guesses from 1,227 addresses.
  • We found no sign that any attack succeeded. The honeypot did reach the PHP2Shell precondition 16 times, from one attacker's oversized uploads, and survived each time.

2. The Setup

The build is described in the first post: an Azure VM running nginx in front of two Docker containers, php:8.3.35-apache (vulnerable) and php:8.3.36-apache (patched, for comparison), with a 2 MB PHP memory limit and session upload progress enabled so that PHP2Shell's preconditions were easy to reach. nginx logged the request line, User-Agent, Content-Type and complete body of every request to Microsoft Sentinel; Apache's own logs and the SSH logs went there too. A rolling packet capture ran alongside.

The container served a static page. No application code read any parameter, which is why we can show every payload in full: nothing on the server could act on them.

4. The Series

  1. PHP2Shell in the Wild: Every Attempt, Decoded
    83 PHP2Shell requests from seven actors, in full: session-file seeding, a broken RedTail loader, 16 out-of-memory fatals during request startup, and the session files they left behind.
  2. RedTail Cryptominer Bot: Full Payload and Dropper Analysis
    The libredtail-http bot, decoded: five legacy exploits in 15 seconds, a payload that carries its own SSH private key, and the dropper script behind it.
  3. React2Shell Payloads: Seven Variants, Decoded
    58 React2Shell exploit requests against a server with no React. Seven different payloads in full: reverse shell, in-memory redirect hijack, .env theft, dropper and three scanner checks.
  4. IoT Botnet Droppers on a PHP Server, Decoded
    137 router, camera and NAS exploits against a PHP server: a 19-exploit loader with progress beacons, a callback scanner, Mozi bots still spreading, and a payload hidden in a header.
  5. One IP, Many Exploits: Spray Scanners
    52 addresses sent 80% of all exploit attempts. Inside the kits: SNIPPER, ReconX canaries, arithmetic execution checks, a slow VPN fingerprint, and kits that ran unchanged from 11 IPs.
  6. Six Old PHP RCEs Still Being Scanned, With Payloads
    PHPUnit eval-stdin, PHP-CGI argument injection, ThinkPHP 5, pearcmd, Apache traversal and Laravel Ignition: every payload we received, decoded.
  7. .env and .git Hunters: 884 Paths, 114 Scanners
    A third of all honeypot traffic was a plain GET for a secrets file. The 884 paths, the scanners behind them, and the AndroxGh0st POST that travels with /.env.
  8. Scanners Are Now Hunting AI Keys and MCP Servers
    178 requests for AI API keys, coding-agent token files and MCP endpoints, on a server that has none. Every path, plus a captured MCP initialize request.
  9. 131,113 SSH Brute-Force Attempts: What the Logger Really Caught
    131,113 guesses, 1,227 IPs, 3,181 usernames — and a PAM logger that only ever saw OpenSSH's decoy password. What it still revealed.
  10. Not Everything on Port 80 Is HTTP
    TLS on port 80, fake RAT victims hunting for malware controllers, and a 17-protocol census (RDP, MongoDB, Siemens S7, DNP3, MQTT...) that nginx never saw. Every probe decoded.
  11. Qualys Scan vs. Real Attackers
    A Qualys scan sent 11,262 requests in 31 minutes; attackers sent 10,509 in 18 days. The scanner never asked for /.env or tested PHP2Shell. Attackers never tried Log4Shell.
  12. A Census of Internet Scanners
    The first visitor came 33 minutes after start-up. Every scanner that named itself: who arrived when, what each asked for, and which "research" scanners went straight for .env files.

5. What We Learned

  • Exposure is immediate. 33 minutes to the first visitor, 86 addresses in the first day. There is no quiet period in which an unpatched server can be "fixed later".
  • New bugs reach attackers' kits in days, and old ones never leave. PHP2Shell was in a cryptominer's loader two days after disclosure. PHPUnit's 2017 bug was the most-tried code execution exploit of all, with 430 requests.
  • Secrets are the main target. More requests asked for .env and .git files than for every exploit put together. A leaked .env needs no vulnerability at all.
  • Most attackers do not check what they are attacking. Router, camera, Java and Node.js exploits all arrived at a PHP server. That makes them easy to detect: an exploit for software you do not run is a free signal.
  • Logs see less than you think. nginx missed a Mozi payload that lived in a request header, every non-HTTP probe that the scanner itself reset, and the body of every request over its buffer size. The packet capture caught what the logs did not.
  • A clean scanner report is not the attackers' view. The Qualys scan never asked for /.env and had no PHP2Shell check; attackers asked for .env 318 times and sent 83 PHP2Shell requests.
  • Exploit quality varies. The RedTail PHP2Shell exploit was malformed and could not have worked anywhere. Botnet nodes kept spraying broken download addresses for weeks. Not every attack in your logs is a working one, but you cannot tell which from the logs alone.

6. What We Could Not Prove

  • Packets for most of the period are gone. The rolling capture held about a day and a half and was overwritten. We have full packets only for 15–16 November, and use them where they add something (React2Shell, IoT and non-HTTP posts).
  • Some headers and bodies were not logged. Cookies and most headers were not in the nginx log format, and bodies over nginx's buffer size were logged empty. Where that matters, the posts say so.
  • We did not fetch second stages. Download URLs in payloads were never requested. Where a binary reached the VM by another route, we hashed it and read its strings on the VM without running it.
  • Attribution is limited to what the traffic says. Scanner names are as given in User-Agents; country is IP geolocation.
  • Since the 15 November restart, the patched container has been answering. The two containers swapped addresses when the VM came back, so nginx now forwards to PHP 8.3.36. All analysis of attacks on the vulnerable build uses the period before that.

7. Data and Methods

Every number in the series comes from the logs, recomputed from the exact nginx log file after we found that our Sentinel copy had replaced every ; with a space. Requests were classified by a fixed set of rules (first match wins) and then reviewed by hand for each post. Payloads are shown as captured, with only these changes: URLs and malicious domains are defanged (hxxp://, [.]), real credentials are masked, and very long padding is shortened where marked. KQL in each post is written for the same Sentinel table layout (Syslog rows with a JSON message prefixed php_http:) and needs adjusting for other log formats.
