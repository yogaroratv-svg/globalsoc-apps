1. How TLS 1.3 & JA4 Fingerprinting Work — Explained Two Ways

Way 1: The Plain-English Analogy (The Unencrypted Menu Card)

In Part 1, our client (115.129.50.130) and our honeypot server (20.248.231.206) knocked on the door and shook hands using TCP (`SYN` → `SYN-ACK` → `ACK`). Now the door is open (`ESTABLISHED`), and we want to talk privately using TLS 1.3 encryption.

But before two computers can speak in secret code, they have to agree on which secret code to use! So the very first message your computer sends—called the TLS ClientHello—must be sent completely unencrypted in plain sight. It is like handing a waiter a printed menu card listing:

  • Which TLS version you speak (e.g., TLS 1.3)
  • Which website name you are visiting (the SNI field)
  • Which encryption ciphers you know (e.g., TLS_AES_128_GCM_SHA256)
  • Which optional features (Extensions) and key-exchange math (e.g., X25519) you support

What is JA4? Because every program (Chrome, Safari, Python, Go, curl, or our custom assembly binary) prints its menu card in a slightly different way, security defenders take a snapshot of your unencrypted ClientHello menu card and turn it into a 36-character barcode called a JA4 Fingerprint (`JA4_a` _ `JA4_b` _ `JA4_c`). Even after the rest of the conversation turns into encrypted gibberish, that JA4 barcode tells the defender what kind of software is knocking at the door!

Way 2: The Technical Formula (`JA4_a` _ `JA4_b` _ `JA4_c`)

When our honeypot (`20.248.231.206`) receives our assembly ClientHello from `115.129.50.130`, it parses the raw bytes and computes the 3 parts of the JA4 string (`t13n010400_0f2cb44170f4_f86e416269f0`):

JA4 Part Value in Our Assembly Packet Exact Byte-by-Byte Calculation
JA4_a
(10 characters)		 t13n010400 • t = Transport protocol is TCP (q if QUIC)
• 13 = Highest version in supported_versions extension (0x002b) is TLS 1.3 (0x0304)
• n = No SNI extension (d = Domain name present, i = Raw IP address in SNI)
• 01 = 1 Cipher Suite offered (0x1301)
• 04 = 4 TLS Extensions offered (002b, 000a, 000d, 0033)
• 00 = No ALPN extension (would be h2 for HTTP/2)
JA4_b
(12 hex chars)		 0f2cb44170f4 Take all Cipher Suite hex codes ("1301"), sort them in ascending order, and take the first 12 characters of the SHA-256 hash:
SHA256("1301")[:12] = 0f2cb44170f4
JA4_c
(12 hex chars)		 f86e416269f0 Sort the hex codes of the Extensions (excluding SNI 0000 and ALPN 0010), append an underscore _, append the Signature Algorithms in their original order (0804), and take the first 12 characters of the SHA-256 hash:
SHA256("000a,000d,002b,0033_0804")[:12] = f86e416269f0

2. The "Russian Nesting Doll" Rule: Changing 1 Cipher to 2 Ciphers in Assembly

What happens if we edit our assembly code (`raw_tcp_tls_ja4.s`) to offer 2 Cipher Suites (0x13, 0x01, 0x13, 0x02) instead of 1 Cipher Suite (0x13, 0x01)?

If you simply insert the 2 bytes 0x13, 0x02 into the middle of your assembly file without updating anything else, the server will immediately reject your packet as corrupted! Why? Because a TLS packet is built like 5 Russian nesting dolls stacked inside each other, and each outer doll has a length number stating how many bytes are inside it.

When you add 2 bytes to the Cipher Suites list, you must add +2 to all 5 length fields from the inside out:

Nesting Level (Inside → Out) 1 Cipher (1301) 2 Ciphers (1301, 1302) Where in raw_tcp_tls_ja4.s
1. Cipher Suites Length 2 bytes (0x00, 0x02) 4 bytes (0x00, 0x04) Right before the cipher bytes in the TLS payload
2. ClientHello Handshake Length 108 bytes (0x00, 0x00, 0x6c) 110 bytes (0x00, 0x00, 0x6e) Bytes 6–8 of the TLS payload (after 0x01 ClientHello tag)
3. TLS Record Length 112 bytes (0x00, 0x70) 114 bytes (0x00, 0x72) Bytes 3–4 of the TLS payload (after 0x16, 0x03, 0x01)
4. IPv4 Total Packet Length 157 bytes (0x00, 0x9d) 159 bytes (0x00, 0x9f) Offset 0x02 of the IPv4 Header (mov word ptr [rip + raw_pkt + 0x02], 0x9f00)
5. TCP Pseudo-Header & sendto Length 137 TCP / 157 Total 139 TCP / 159 Total mov r14, 139 (TCP+TLS len), mov r15, 76 (words), mov rdx, 159 (sendto bytes)

Live Result in Our Honeypot Logs (`tls_attacks.jsonl`)

  • With 1 Cipher (`0x1301`): t13n010400_0f2cb44170f4_f86e416269f0
  • With 2 Ciphers (`0x1301, 0x1302`): t13n020400_62ed6f6ca7ad_f86e416269f0

Notice how the cipher count changed from 01 to 02, the middle hash (`JA4_b`) changed completely (`SHA256("1301,1302")[:12] = 62ed6f6ca7ad`), and the last hash (`JA4_c`) stayed 100% identical (`f86e416269f0`) because we didn't touch the extensions!

3. Real Packet Captures from `115.129.50.130` → `20.248.231.206`

During our live assembly testing from `115.129.50.130` to `20.248.231.206`, we captured two classic TLS 1.3 edge cases in our PCAP logs:

Discovery A: What Happens When `key_share` (`0x0033`) Is Empty? (`HelloRetryRequest`)

At 08:43:18 UTC, our initial 85-byte ClientHello from `115.129.50.130` sent an empty key_share extension (`00 33 00 02 00 00`). Because TLS 1.3 wants to encrypt the handshake immediately, the honeypot (`20.248.231.206`) could not compute a shared secret yet. Instead of crashing, OpenSSL sent back an RFC 8446 HelloRetryRequest—which looks like a ServerHello whose 32-byte random field is hardcoded to the SHA-256 hash of the ASCII string "HelloRetryRequest":

CF 21 AD 74 E5 9A 61 11 BE 1D 8C 02 1E 65 B8 91
C2 A2 11 16 7A BB 8C 5E 07 9E 09 E2 C8 A8 33 9C

Our client immediately responded with a second, 121-byte ClientHello containing a 32-byte X25519 public key (`0x001d`)! In raw_tcp_tls_ja4.s, we include that 32-byte X25519 public key right inside the very first ClientHello so the handshake succeeds in a single round-trip.

Discovery B: Why Signature Algorithm `0x0403` Failed, and `0x0804` Succeeded!

When our client advertised both 0x0403 (`ecdsa_secp256r1_sha256`) and 0x0804 (`rsa_pss_rsae_sha256`), or mismatched the server's RSA-2048 certificate, we tested removing `0x0403` so the `signature_algorithms` extension (`0x000d`) requested `0x0804` (`rsa_pss_rsae_sha256`). That changed `JA4_c` from `3cd5d6589845` to `f86e416269f0`, completed the full ECDH X25519 + HKDF-SHA256 handshake from `115.129.50.130`, and delivered the encrypted application payload:

JA4 Fingerprint:   t13n010400_0f2cb44170f4_f86e416269f0

4. How `raw_tcp_tls_ja4.s` Sends Packet 4 (`PSH-ACK` + 117-Byte TLS `ClientHello`)

Right after Step 3 (`ACK`) finishes in `raw_tcp_tls_ja4.s`, we reuse the exact same buffer (`raw_pkt`) to send Packet 4 containing our 117-byte TLS 1.3 `ClientHello`:

    # =========================================================================
    # PACKET 4: Send 157-Byte Raw TCP + TLS 1.3 ClientHello (Flag = 0x18 PSH+ACK)
    # Source IP: 115.129.50.130 -> Dest IP: 20.248.231.206
    # =========================================================================
    # 1. Update IPv4 Total Length from 40 bytes to 157 bytes (0x009d -> 0x9d00 little-endian)
    mov word ptr [rip + raw_pkt + 0x02], 0x9d00

    # 2. Update TCP Flags from 0x10 (ACK) to 0x18 (PSH + ACK = Push TLS Data to Application!)
    mov byte ptr [rip + raw_pkt + 0x21], 0x18

    # 3. Update Pseudo-Header TCP Segment Length to 137 bytes (20B TCP + 117B TLS = 0x0089)
    mov word ptr [rip + pseudo_buf + 0x0A], 0x8900

    # 4. Recompute TCP Checksum over 12B Pseudo-Header + 20B TCP + 117B TLS Payload
    mov r14, 137                    # Copy 137 bytes (20B TCP + 117B TLS) into pseudo_buf+12
    mov r15, 75                     # Sum 75 16-bit words (12B pseudo + 137B TCP/TLS + 1B pad = 150B)
    call calc_tcp_csum

    # 5. Transmit all 157 bytes over the Raw Socket!
    mov rax, 44                     # sys_sendto
    mov rdi, r12
    lea rsi, [rip + raw_pkt]
    mov rdx, 157
    xor r10, r10
    lea r8, [rip + dst_addr]
    mov r9, 16
    syscall
