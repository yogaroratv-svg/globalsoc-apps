1. Why TLS Handshakes Overwhelm Servers — Explained Two Ways

Way 1: The Coffee Shop Counter & Waiting Room Analogy

Imagine a coffee shop with one barista (our Python honeypot process on 20.248.231.206) and a small waiting room that only holds 100 chairs (server.listen(100)):

  • For the Customer (The Sender): Shouting "One cappuccino, please!" (sending a 285-byte Chrome ClientHello) takes zero effort. You don't have to grind beans or steam milk; you just say the words.
  • For the Barista (Our Honeypot Server): Every time someone shouts an order, the barista has to grind the beans, steam the milk, pour the cup, and write a receipt (parse the TLS packet, compute SHA-256 JA4/JA3 hashes, run heavy OpenSSL Elliptic Curve X25519 + RSA-2048 cryptography, send back 1,546 bytes of certificates, and write to disk). That takes 2 milliseconds of hard work per order.
  • 50 Customers One-by-One (Polite Line): If 50 customers walk in one after another, each gets their coffee in 2 milliseconds, and all 50 are done in 0.105 seconds.
  • 1,000 Customers at the Exact Same Millisecond (The Stampede): If 1,000 people rush the door at the exact same instant and refuse to leave for half a second, 500+ people cram inside, the 100 waiting-room chairs overflow immediately, and 233 people get locked outside on the street (`TimeoutError`) while everyone inside waits over 1 to 5.4 seconds!

Way 2: The Technical Asymmetry (0 ms Sender CPU vs. 80 ms Server CPU)

When we ran our 50-request test (`test_50_sni_cpu.py`) rotating through 5 travel domains (skyscanner.com, bravofly.com, expedia.com, booking.com, qantas.com), look at the resource imbalance between the sender and the server:

  1. CPU Imbalance: Sending 50 static ClientHello packets used 0.0 ms of CPU on the sender, while forcing the honeypot server to burn 80.0 ms of pure CPU time in just 105 ms of wall-clock time (76.4% of a CPU core).
  2. Network Traffic Amplification (5.4x): The sender transmitted just 14,280 bytes (~285 bytes/request), while the honeypot had to generate and transmit 77,300 bytes (~1,546 bytes/reply containing the `ServerHello`, TLS 1.3 EncryptedExtensions, Certificate, and CertificateVerify signature).
  3. Why Spoofing Chrome's JA4 Makes Floods Worse for Defenders: If an attacker floods a server using our stripped-down assembly packet (`t13n010400...`), a firewall can drop that JA4 before it ever reaches the server's CPU. But if the flood uses Google Chrome's exact JA4 (`t13d1514h2...`), blocking that JA4 would block every real customer using Chrome! Defenders must combine JA4 with per-IP rate limiting.

2. How We Monitored a 0.1-Second CPU Spike Using `/proc/1/stat`

All 50 requests finished in 0.105 seconds (105 milliseconds). If you ran top, htop, or kubectl top pod, you would miss the spike completely because top only refreshes every 1 to 3 seconds!

Instead, our Python script (`test_50_sni_cpu.py`) queries the Linux Kernel directly by reading /proc/1/stat right before Request #1 and right after Request #50:

def get_honeypot_stats():
    # Inside our Kubernetes container, honeypot_server.py is Process ID 1 (PID 1).
    # The Linux kernel exposes real-time CPU, thread, and RAM accounting in /proc/1/stat.
    with open("/proc/1/stat") as f:
        parts = f.read().split()

    utime       = int(parts[13])      # Column 14: User-space CPU ticks (Python + OpenSSL math)
    stime       = int(parts[14])      # Column 15: Kernel-space CPU ticks (TCP sockets + disk I/O)
    num_threads = int(parts[19])      # Column 20: Active concurrent threads inside the server
    rss_kb      = int(parts[23]) * 4  # Column 24: Resident RAM pages currently allocated (4 KB/page)
    return utime + stime, num_threads, rss_kb  # 1 kernel tick = 10 milliseconds (1/100th sec)

3. How the Code Dynamically Swaps SNI Domains Without Breaking JA4

When rotating between "qantas.com" (10 letters) and "skyscanner.com" (14 letters), the SNI extension changes length. Our function `build_chrome_client_hello(domain_str)` recalculates the 3 nested SNI length headers automatically using `L = len(domain)`:

def build_chrome_client_hello(domain_str):
    domain = domain_str.encode('ascii')
    L = len(domain)

    # Pack SNI payload: List Length = L + 3, Type = 0 (DNS Hostname), Hostname Length = L
    sni_payload = struct.pack('!HBH', L + 3, 0, L) + domain
    ext_sni     = struct.pack('!HH', 0x0000, len(sni_payload)) + sni_payload

4. Final Benchmark Results: 50 One-by-One vs. 1,000 at the Exact Same Instant

Using `test_1000_concurrent_tls.py` (`asyncio.Event()`), we lined up 1,000 coroutines at a starting gate and released all 1,000 Chrome TLS requests at the exact same millisecond. Here is the side-by-side comparison:

Measurement 50 Requests (One-by-One) 1,000 Requests (Same Instant!) Why This Happened Inside the Server
Total Wall Time 0.105 seconds 6.187 seconds Massive queue bottleneck + 5-second TCP timeouts.
Successful Handshakes 50 / 50 (100%) 767 / 1,000 (76.7%) 233 connections failed completely (TimeoutError) because the `listen(100)` TCP backlog waiting room overflowed!
Average Handshake Latency 2.06 ms 1,033.7 ms (1.03 sec!) 500x slowdown! Every request got stuck waiting for OpenSSL CPU time.
Worst Handshake Latency 5.94 ms 5,414.8 ms (5.41 sec!) Some visitors waited over 5.4 seconds just to receive `ServerHello`.
Active Server Threads 3 threads 3 → 514 threads! The honeypot was forced to spin up 511 concurrent Python threads at once.
Server RAM Used (RSS) 52.9 MB (Flat) 52.9 MB → 63.5 MB (+10.5 MB) Those 514 threads + OpenSSL contexts consumed an extra 10.5 MB of RAM in half a second.
CPU Time Burned 80 ms (Server) vs 0 ms (Sender) 2,140 ms (Server) vs 370 ms (Sender) The server burned 2.14 full seconds of pure CPU (~6x more than the sender).
Key Kubernetes Lesson: High CPU Freezes a Pod; High RAM Kills It (`OOMKilled`)

Notice that pinning the CPU and overflowing `listen(100)` caused 233 visitors to time out and slowed the server down by 500x—making it look "down" to users—without Kubernetes deleting the pod. Kubernetes only kills and restarts a pod (`OOMKilled`) when concurrent threads and OpenSSL buffers push RAM (`RSS`) past the container's memory limit!
