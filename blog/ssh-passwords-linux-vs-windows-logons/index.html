11,397 Real SSH Passwords From a Honeypot That Said Yes, and How Linux Logon Telemetry Differs From Windows

We let PAM accept any password for 40 decoy accounts and logged every password typed: 11,397 real passwords, 2,391 unique, from 151 IPs, including the same 416-username botnet seen on our PHP honeypot. Then we compared what auth.log, MDE DeviceLogonEvents and Falcon record on Linux with what Windows 4624/4625 give you, and where each one goes blind.

Key Sections: How the Passwords Were Captured · The Numbers · The Botnet With a 416-Name List · Linux vs Windows Logons · What MDE Misses on Linux · Pyramid of Pain · Detections · When It Fires · IOCs

Data window: 29 October – 11 November 2026 (on-host logs effectively end on 2 November when the disk filled; MDE covers the full window), the Cisco ASA honeypot from the SSH tunnel and after-login posts. Part of my honeypot detection series. Org A runs Microsoft Defender for Endpoint with Microsoft Sentinel; queries marked Tested ran against this honeypot's MDE data. Org B runs Splunk with CrowdStrike Falcon; its queries were not run against this data. The Windows columns in section 4 describe documented Windows and MDE behaviour for comparison; this honeypot was Linux only.

1. How the Passwords Were Captured

sshd never logs passwords. To see them, the honeypot put a PAM module in front of the real authentication:

# /etc/pam.d/sshd (top of file)
auth optional   pam_exec.so expose_authtok /usr/local/bin/log-ssh-password.sh
auth requisite  pam_succeed_if.so user notin root:labadmin
auth sufficient pam_permit.so
@include common-auth

pam_exec ... expose_authtok hands the typed password to a script on stdin, which wrote timestamp | IP | user | RawHex | Str to a log. pam_succeed_if user notin root:labadmin stops the stack for the two real accounts (they fall through to normal pam_unix, so root could never be guessed). For everyone else pam_permit says yes: any password works for the 40 decoy accounts created for the honeypot (UIDs 1001–1040 in /etc/passwd), and, as the logs showed, for built-in system accounts too: backup, bin, sshd, sync and www-data all accepted logins, because pam_permit doesn't care what the account is for.

One OpenSSH detail decides how you read the log. When a client names a user that doesn't exist, sshd still runs PAM so the timing doesn't leak which usernames are valid, but it replaces the password with a fixed decoy, \b\n\r\177INCORRECT, repeated or cut to the length the client typed (fake_password() in auth-pam.c). So for invalid users you learn the length of the password and nothing else. 8,353 of the 19,750 captured entries were that decoy. Count them as real and you inflate the password list with strings like \b\n\r\177IN; check for the decoy at every length, not just 13 bytes (my first pass only checked prefixes of the 13-byte string and over-counted by 79).

3. The Botnet With a 416-Name List

Ten IPs in 109.160.32[.]0/24 each sent 1,196 or 1,197 passwords and each tried exactly 416 usernames (one tried 415). That is the same 416-username list I found on the PHP honeypot in October (SSH brute-force post), from the same /24, against a different VM on a different public IP. On the PHP box I could only see the usernames. Here PAM shows the passwords that go with them, and because the decoy accounts said yes, MDE shows what each worker did with a success: 109.160.32[.]200 logged into 29 different accounts with 297 successful logons; .179, .160 and .105 did the same. A worker run typically lasted one to two hours; then the next worker in the pool started.

After a success the worker ran one command, uname -s -v -n -r -m or uname -m | awk '{printf $1}', and disconnected (see the after-login post). The success is reported upstream; someone else comes back to use it. In this dataset that someone ran an SSH tunnel for 12 days.

The practical consequence: Windows logon detections lean on fields (logon type, SubStatus, workstation, package). Linux SSH detections have to lean on sequences and shapes (failures then success from one IP, one IP succeeding on many accounts, many IPs from one /24 sharing a list, sessions that last seconds or days), because the fields aren't there.

5. What MDE Misses on Linux

The two sources don't cover the same period. The honeypot's disk filled up around 2–3 November, so auth.log and the PAM password log effectively stop there (PAM entries per day: 5,110 on 1 Nov, 615 on 2 Nov, then about 40 a day). MDE streams off the box and kept recording until 11 November. Comparing totals across the whole fortnight is therefore meaningless; here is the like-for-like window, 29 October – 1 November, plus what MDE alone saw afterwards:

Event (external sources)auth.log 29 Oct – 1 NovMDE DeviceLogonEvents 29 Oct – 1 NovMDE 2 – 11 Nov
Successful SSH logins~3,400 Accepted1,991 Network rows (one per LogonId; each also gets a separate Local row for the PAM session)5,860
Failed passwords for root~7,800391 (~5%)exactly 100 per day, 1 – 9 Nov

Failed passwords for existing non-root accounts10 (before PAM accepted any password)4 (deploy, debian, ubuntu, vpn from 109.160.32[.]200, 29 Oct 21:17–21:18, two minutes before the decoy PAM stack went live)0

On this sensor, MDE recorded fewer successful logins than sshd, a small sample of failures for accounts that exist, none for usernames that don't, and a flat 100 root failures per day on every day after 1 November, which looks like per-device throttling (my inference from the shape; I have not found it documented). If your SSH brute-force detection runs only on DeviceLogonEvents, you are looking at a sample of the guessing and none of the username enumeration. Forward auth.log to the SIEM as well (Syslog via AMA for Org A, the Unix and Linux add-on for Org B) and build the volume and shape rules there.

7. Detections

D1. One source succeeds on three or more local accounts (T1110.001, T1078.003)

Org A Tested: 83 source IPs. The top five each logged into 29 accounts: 109.160.32[.]200 (297 logons), 109.160.32[.]179, 77.239.124[.]156, 109.160.32[.]160, 109.160.32[.]105.

// A1 (MDE): one source IP succeeds on several different local accounts (password reuse / default creds / honeypot-style acceptance)
DeviceLogonEvents
| where Timestamp > ago(30d)
| where ActionType == "LogonSuccess" and LogonType == "Network" and RemoteIPType == "Public"
| summarize Accounts = dcount(AccountName), AccountList = make_set(AccountName, 20), Logons = count(),
            First = min(Timestamp), Last = max(Timestamp) by DeviceName, RemoteIP
| where Accounts >= 3
| order by Accounts desc

Org B

`comment("B1: linux_secure - one source succeeds on 3+ local accounts")`
index=linux sourcetype=linux_secure process=sshd "Accepted"
| rex "Accepted (?<method>\S+) for (?<user>\S+) from (?<src>\d+\.\d+\.\d+\.\d+)"
| stats dc(user) as accounts values(user) as account_list count as logons min(_time) as first max(_time) as last by host src
| where accounts>=3
| convert ctime(first) ctime(last)

On a normal server one IP logs into one account. Three distinct local accounts from one internet IP in a month is either a jump host you know about or a password list that worked more than once.

D2. A /24 of workers on one host

Org A Tested: 2 networks: 77.239.124[.]0/24 (34 workers, 1,941 logons) and 109.160.32[.]0/24 (28 workers, 3,783 logons).

// A2 (MDE): a /24 of workers all logging into the same host
DeviceLogonEvents
| where Timestamp > ago(30d) and ActionType == "LogonSuccess" and LogonType == "Network" and RemoteIPType == "Public"
| summarize Accounts = dcount(AccountName), Logons = count() by DeviceName, RemoteIP
| extend Net24 = strcat(tostring(split(RemoteIP, ".")[0]), ".", tostring(split(RemoteIP, ".")[1]), ".", tostring(split(RemoteIP, ".")[2]), ".0/24")
| summarize Workers = dcount(RemoteIP), AccMin = min(Accounts), AccMax = max(Accounts), Logons = sum(Logons) by DeviceName, Net24
| where Workers >= 10 and AccMax >= 10

Org A Sentinel Syslog version on failures (sees the invalid-user guesses MDE drops):

// A5 (Sentinel Syslog): same username list split across a /24 (wordlist workers)
Syslog
| where ProcessName == "sshd" and SyslogMessage startswith "Failed password"
| extend SrcIp = extract(@"from (\d+\.\d+\.\d+\.\d+)", 1, SyslogMessage),
         User = extract(@"for (?:invalid user )?(\S+) from", 1, SyslogMessage)
| summarize Users = dcount(User), Attempts = count() by SrcIp
| extend Net24 = strcat(tostring(split(SrcIp, ".")[0]), ".", tostring(split(SrcIp, ".")[1]), ".", tostring(split(SrcIp, ".")[2]))
| summarize Workers = dcount(SrcIp), UsersMin = min(Users), UsersMax = max(Users), AttemptsMin = min(Attempts), AttemptsMax = max(Attempts) by Net24
| where Workers >= 5 and UsersMax - UsersMin <= 5

Org B

`comment("B2: linux_secure - wordlist workers: one /24, identical username counts")`
index=linux sourcetype=linux_secure process=sshd "Failed password"
| rex "for (?:invalid user )?(?<user>\S+) from (?<src>\d+\.\d+\.\d+\.\d+)"
| stats dc(user) as users count as attempts by src
| rex field=src "^(?<net24>\d+\.\d+\.\d+)\."
| stats dc(src) as workers min(users) as users_min max(users) as users_max min(attempts) as att_min max(attempts) as att_max by net24
| where workers>=5 AND users_max-users_min<=5

D3. Failures, then success, from the same source (T1110 → T1078)

Org A Tested on MDE: 0 rows. Not because it didn't happen, but because of section 5: MDE logged failures mostly for root, which never succeeded, and the only other accounts with recorded failures had one each (below the rule's threshold of 3). On Linux, run this rule on sshd syslog:

// A3 (MDE, Linux caveat): failures MDE CAN see - existing accounts only - followed by a success from the same IP
DeviceLogonEvents
| where Timestamp > ago(30d) and LogonType == "Network"
| summarize Fails = countif(ActionType == "LogonFailed"), Succ = countif(ActionType == "LogonSuccess"),
            FirstFail = minif(Timestamp, ActionType == "LogonFailed"), FirstSucc = minif(Timestamp, ActionType == "LogonSuccess")
          by DeviceName, RemoteIP, AccountName
| where Fails >= 3 and Succ > 0 and FirstSucc > FirstFail
// A4 (Sentinel Syslog): the full picture MDE misses on Linux - invalid users and every failure
let Ssh = Syslog
| where ProcessName == "sshd"
| extend Outcome = case(SyslogMessage startswith "Failed password", "Failed", SyslogMessage startswith "Accepted", "Accepted", "")
| where isnotempty(Outcome)
| extend SrcIp = extract(@"from (\d+\.\d+\.\d+\.\d+)", 1, SyslogMessage),
         User = extract(@"for (?:invalid user )?(\S+) from", 1, SyslogMessage),
         Invalid = SyslogMessage has "invalid user";
Ssh
| summarize Failed = countif(Outcome == "Failed"), InvalidUserFails = countif(Invalid), Accepted = countif(Outcome == "Accepted"),
            Users = dcount(User), AcceptedUsers = make_set_if(User, Outcome == "Accepted", 20)
          by Computer, SrcIp, bin(TimeGenerated, 1d)
| where Accepted > 0 and Failed >= 10

Org B Falcon (event names for Linux logon telemetry vary by sensor version; confirm UserLogon/UserLogonFailed2 exist for Linux hosts in your tenant before relying on it). The linux_secure version of the same rule is L3 in the SSH brute-force post.

`comment("B3: Falcon - Linux SSH logons by source (UserLogon / UserLogonFailed2; check event names in your tenant)")`
event_platform=Lin event_simpleName IN (UserLogon, UserLogonFailed2)
| stats count(eval(event_simpleName="UserLogon")) as success count(eval(event_simpleName="UserLogonFailed2")) as failed
        dc(UserName) as accounts values(UserName) as users by aid ComputerName RemoteAddressIP4
| where success>0 AND (failed>=3 OR accounts>=3)

D4. For contrast: the Windows rule you already have

The same intent on Windows is one event ID with the reason in a field. This is what the Linux rules above have to reconstruct from text.

Org A

// Windows equivalent for contrast (Org A, Sentinel SecurityEvent): failures split by reason
SecurityEvent
| where EventID == 4625
| extend Code = tolower(iff(SubStatus in~ ("0x0", ""), Status, SubStatus))   // locked/disabled often only in Status
| extend Reason = case(Code == "0xc0000064", "no such user", Code == "0xc000006a", "bad password",
                       Code == "0xc0000234", "locked out", Code == "0xc0000072", "disabled", Code)
| summarize Fails = count(), Users = dcount(TargetUserName), Workstations = make_set(WorkstationName, 10)
          by IpAddress, LogonType, AuthenticationPackageName, Reason, bin(TimeGenerated, 1h)

Org B

`comment("Windows equivalent for contrast (Org B, Splunk WinEventLog)")`
index=wineventlog EventCode=4625
| eval code=lower(if(Sub_Status="0x0" OR isnull(Sub_Status), Status, Sub_Status))
| eval target_user=mvindex(Account_Name, 1)
| eval reason=case(code="0xc0000064","no such user", code="0xc000006a","bad password",
                   code="0xc0000234","locked out", code="0xc0000072","disabled", true(), code)
| bin _time span=1h
| stats count dc(target_user) as users values(Workstation_Name) as workstations by _time Source_Network_Address Logon_Type Authentication_Package reason

8. When It Fires

  • D1 or D3 on a real server: the password worked. Lock the account, kill its sessions (Org A Live Response, Org B RTR), then pull the session's commands and network connections: the after-login and tunnel posts show what to look for.
  • D2: no single IP is interesting; the list is. Take the usernames the pool tried (Syslog/linux_secure) and check every Linux host for those accounts with password authentication enabled.
  • Check the account names in section 2 against your estate, especially claude, openclaw, codex and agent users created so an AI agent can SSH in. They are on the lists now.
  • Turn off PasswordAuthentication on internet-facing SSH. Every login in this dataset was a password.
