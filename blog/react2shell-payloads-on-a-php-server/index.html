React2Shell on a Server With No React: Seven Payloads, Decoded

Attackers sent 58 React2Shell (CVE-2025-55182) exploit requests to a PHP honeypot that runs no JavaScript at all. Because nothing was at risk, we can show every payload in full: three scanner checks, a wget dropper, an environment-variable stealer, an in-memory redirect hijack, and one reverse shell that was retried 51 times.

Key Sections: Summary · How the Exploit Request Works · Scanner Checks · Dropper · Environment Theft · Redirect Hijack · Reverse Shell x 47 · What the Honeypot Answered · Reverse Shell on the Wire · IOCs · Detection (KQL) · Mitigation

Part of the PHP honeypot series. Data: nginx request log from vm-php-cve-lab, 22 October – 15 November 2026 (UTC; the VM was switched off from 9 to 15 November). Payloads are shown as captured; URLs are defanged.

1. Summary

React2Shell is CVE-2025-55182, a remote code execution flaw in React Server Components disclosed in December 2025 with a CVSS score of 10.0. One unauthenticated POST to any page of a vulnerable Next.js App Router application runs JavaScript inside the Node.js server process.

Our honeypot is Apache with PHP. It has no Node.js, no React and no Next.js. It still received 58 React2Shell requests from 11 IPs between 2026-10-22 and 2026-11-09. Every one was a POST /, and every one got the same static page back with status 200.

That makes this a clean sample. The attackers did not fingerprint the target first; they sent the exploit to port 80 and moved on. Since nothing could execute, we kept the complete request for each of seven distinct payloads:

It is a multipart form with three fields named 0, 1 and 2. That is the wire format React uses when a browser calls a Server Action: each field is a "chunk" of a serialised object graph, and chunks refer to each other with $ prefixes. The server-side decoder trusted those references too much.

Part of the payloadWhat it does
Field 1 = "$@0"$@ means "give me chunk 0 itself, as the internal promise-like object", not its decoded value. This hands the attacker's JSON to code that expects a real internal Chunk.
"then":"$1:__proto__:then"A reference with a path. It walks from chunk 1 up to __proto__ and takes the real Chunk.prototype.then. The fake object now has a genuine then method, so React treats it as a promise and awaits it. The decoder did not stop property paths from reaching the prototype; that is the bug.
"status":"resolved_model"Tells that then method the chunk is ready to be parsed. It parses value using the object in _response as its context, and _response is attacker data.
"value":"{\"then\":\"$B1337\"}"$B is a Blob reference. To resolve it the decoder calls _response._formData.get(_response._prefix + "1337").
"_formData":{"get":"$1:constructor:constructor"}Another prototype walk: the constructor of the constructor of any object is Function. So the call above becomes Function(_prefix + "1337"), which compiles the attacker's string into a function.
"_prefix":"…"The JavaScript to run. The decoder appends the blob id, so the code ends with a statement separator and the stray 1337 is a harmless expression. The new function is stored as a then property, React awaits it, and it runs.

One thing is missing from our copy. A real attack also needs a Next-Action request header so that Next.js routes the POST to the Server Action decoder. Our nginx log format recorded the request line, User-Agent, Content-Type and body only, so that header is not in the log. The packet capture in section 9 shows it on four later attempts: Next-Action: x.

Getting output back. Most payloads end by throwing an error named NEXT_REDIRECT with a digest string. Next.js uses exactly that error internally to implement redirect(). When it sees one, it answers with a redirect and copies the target into an x-action-redirect response header. The attacker puts command output into the target (/login?a=<output>) and reads it from the response header. No outbound connection is needed.

The most unusual of the seven. It does not download anything or steal anything. It takes over the site's traffic:

  1. It loads Node's http module (and https, if present) and replaces Server.prototype.emit, the function every Node HTTP server uses to dispatch events.
  2. The replacement watches for request events. For every GET or HEAD it answers 307 with Location: hxxps://return[.]st/ and stops. The application never sees the request.
  3. All other methods are passed to the original function. POST still works, so the same exploit can be sent again later.
  4. It runs echo lol, then throws a NEXT_REDIRECT so its own response is also a redirect to the same address.

The result on a vulnerable site: every visitor and every search-engine crawler is redirected to the attacker's domain, immediately. Nothing is written to disk. No new process appears. A file-integrity scan, a malware scan of the container image and a look at ps all come back clean, because the change lives only in the memory of the running Node process. Restarting the process removes it, and an unpatched server can be re-infected with one request.

A classic reverse shell in five expressions: start /bin/sh, open a TCP connection to 91.92.40.12 port 12323, and pipe the socket into the shell's input and the shell's output and errors back into the socket. The address it connects to is the address the request came from. There is no check, no marker and no thrown error. The operator learns it worked when a shell connects.

This variant is trimmed: it has no _chunks key and no field 2.

8. What the Honeypot Answered

Status: 200 x 58. Response sizes: 1936 bytes x 50, 3684 bytes x 7, 1941 bytes x 1. Those are the lab's static index page, uncompressed and gzip-compressed. Apache passed the POST to index.php, which ignores its input.

The honeypot does have a PHP multipart parser behind that URL, and the PHP2Shell post is about attacks on it. A React2Shell body is three tiny text fields, with no file part and no session field. PHP parsed it into $_POST['0'], $_POST['1'], $_POST['2'] and discarded it. The container's Apache log shows one ordinary access line per request ("POST / HTTP/1.0" 200) and no PHP warning or error beside it. There is no JavaScript runtime on the host for the payload to reach.

A 200 with an ordinary HTML page is a "not vulnerable" answer to every variant here: none of them got the redirect header or error digest it was looking for.

9. The Reverse Shell on the Wire

The lab ran a rolling packet capture (tcpdump, full snap length, 20 files of 10 MB) on port 80 and the Docker bridges. A ring that small holds about a day and a half of traffic, and the last of it was overwritten on 15 November when the VM was restarted and a large package download passed through the capture filter. The packets for the requests from 22 October to 15 November no longer exist. What remains is the nginx request log (request line, User-Agent, Content-Type and the complete request body) and the Apache log from inside the container, both shipped to Microsoft Sentinel as they were written. Sections 2 to 8 are built from those two sources.

After that loss a new full-packet capture was started on the VM. It covers 15 Nov 2026 09:06:34 to 16 Nov 2026 00:10:59 UTC (500 TCP streams on port 80, plus every packet to or from the container address 172.18.0.2 on any port). That is after the end of the log data used above, and variant G was still coming: 4 more attempts, roughly every three to four hours, which makes 51 in total over 9 days.

Every attempt has the same shape. A bare SYN arrives first, with no TCP options and an implausible TTL. The honeypot answers SYN-ACK and the sender resets. A fraction of a second later a normal Linux TCP stack connects from the same address and sends the exploit:

11. Detection (KQL)

The wrapper is constant, so match on it and not on the command:

Syslog
| where SyslogMessage startswith "php_http: "
| extend j = parse_json(substring(SyslogMessage, 10))
| extend Client = tostring(j.client), Method = tostring(j.method), Uri = tostring(j.uri), Status = toint(j.status), Body = tostring(j.body), CT = tostring(j.content_type)
| where Method == "POST" and CT startswith "multipart/form-data"
| where Body has "__proto__" and Body has "constructor:constructor"
| extend Payload = case(
    Body has "cl.connect" or Body has "net.Socket" or Body has "/dev/tcp", "reverse shell",
    Body has_any ("wget ", "curl ", "| sh", "|sh"), "dropper",
    Body has_any ("cat .env", " env ", "printenv"), "secret theft",
    Body has "Server.prototype.emit", "request hook",
    Body has "execSync" or Body has "spawn", "command execution",
    "marker only")
| project TimeGenerated, Client, Uri, Status, Payload, Boundary = extract(@"boundary=(.+)$", 1, CT), Body
| order by TimeGenerated asc

On a real Next.js server, also look at the response side, which our PHP honeypot could never produce: an x-action-redirect header whose value contains /login?a=, a 303/307 answer to a POST carrying a Next-Action header from a client that never loaded a page, and a Node process spawning sh, wget, curl or opening an outbound socket.

Repeat offenders, like the reverse-shell loop:

Syslog
| where SyslogMessage startswith "php_http: "
| extend j = parse_json(substring(SyslogMessage, 10))
| where tostring(j.body) has "constructor:constructor"
| summarize Attempts = count(), Days = dcount(bin(TimeGenerated, 1d)), First = min(TimeGenerated), Last = max(TimeGenerated), Variants = dcount(hash_sha256(tostring(j.body))) by Client = tostring(j.client)
| order by Attempts desc

12. Mitigation

  • Patch. The fix is in the React Server Components packages (react-server-dom-webpack, -parcel, -turbopack) 19.0.1, 19.1.2 and 19.2.1, and in the Next.js releases that bundle them (15.0.5, 15.1.9, 15.2.6, 15.3.6, 15.4.8, 15.5.7, 16.0.7 or later on each line). Check what is actually deployed with npm ls react-server-dom-webpack next inside the running image, not the repository. Old containers and forgotten preview deployments are what the two-hour loop in section 7 finds.
  • If you were exposed while unpatched, assume the environment was read. Payload F takes one request and leaves no file. Rotate every secret in the process environment and .env, then review provider logs.
  • Restart after patching. Payload D lives in process memory. A patched build that is deployed by restarting clears it; a hot reload may not.
  • Restrict egress from application containers. A web app rarely needs to open connections to arbitrary internet addresses. Default-deny outbound stops the reverse shell (G) and the dropper (E) outright. It does not stop D or F, which return through the HTTP response.
  • Run the app as a non-root user on a read-only filesystem, with no shell or download tools in the image where possible. wget … | sh fails when there is no wget.
  • WAF rule as a stopgap, not a fix: block multipart bodies containing :__proto__: or :constructor:constructor. The fixed PoC boundary is worth a rule too; it caught 54 of the 58 requests here.
  • Alert on your crontab disappearing and on any child process of the Node server.
