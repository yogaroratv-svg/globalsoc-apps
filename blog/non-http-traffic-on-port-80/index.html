Not Everything on Port 80 Is HTTP: 738 Strange Requests and a 17-Protocol Census

Our honeypot's web port received TLS handshakes, HTTP/2 prefaces, fake Gh0st and njRAT victims hunting for malware controllers, and in 15 hours of packet capture probes for 17 other protocols, from RDP and MongoDB to Siemens S7 and DNP3. Most of them never reached nginx at all. Every probe decoded.

Key Sections: Summary · What nginx Writes Down · TLS on Port 80 · HTTP/2 Prefaces · Hunting for RAT Controllers · A 17-Protocol Census · Why nginx Never Saw It · Proxy Checks · Odds and Ends · IOCs · Detection (KQL) · Mitigation

Part of the PHP honeypot series. Data: nginx request log from vm-php-cve-lab, 22 October – 15 November 2026 (UTC), and a packet capture from 15 Nov 09:06 to 16 Nov 00:10 UTC. Byte dumps are from the capture.

1. Summary

Port 80 is the web port, but nothing forces a client to speak HTTP to it. In 24 days nginx logged 738 requests from 286 addresses that were not valid HTTP at all (400 x735, 200 x3). And 15 hours of packet capture showed that most non-HTTP probing never shows up in the web log.

  • 520 were TLS handshakes from 250 addresses: clients trying HTTPS on the plain HTTP port.
  • 94 were HTTP/2 connection prefaces, checking for unencrypted HTTP/2.
  • 13 came from two addresses pretending to be computers infected with the Gh0st and njRAT remote access trojans. A real controller would answer them, and so give itself away.
  • In 15 hours the capture recorded 125 probes for 17 other protocols (RDP, SQL Server, Oracle, MongoDB, Redis, memcached, PostgreSQL, SMB, MQTT, Siemens S7, DNP3, IPMI, PPTP, X11, Niagara Fox, DNS and one we could not identify) from nine addresses. Not one of them reached nginx: the scanner's own operating system reset each connection before the probe was sent.

2. What nginx Writes Down

nginx expects a request line ending in a line break. When the bytes are not HTTP, it answers 400 Bad Request and logs whatever came before the first line break as the "request", with no method, no path and a request size of 0. 3. TLS on Port 80

520 connections from 250 addresses opened with a TLS ClientHello, the first message of an HTTPS connection. Internet-wide scanners try TLS on every open port, because services run HTTPS on all sorts of ports and the only way to find out is to try. nginx answers in plain text:

HTTP/1.1 400 Bad Request
Server: nginx/1.18.0 (Ubuntu)
Date: Sun, 15 Nov 2026 09:33:36 GMT
Content-Type: text/html
Content-Length: 166
Connection: close

<html>
<head><title>400 Bad Request</title></head>
<body>
<center><h1>400 Bad Request</h1></center>
<hr><center>nginx/1.18.0 (Ubuntu)</center>
</body>
</html>

which a TLS client cannot parse, so it gives up. Two ClientHellos in the capture stand out. The one from 91.231.89.212 carries the IP address 13.75.195.138 as its server name; the TLS standard does not allow IP addresses there, and browsers never send one. And the one from 35.214.164.203 has a "random" field that is not random at all: it spells random1random2random3random4 in ASCII. Both are easy fingerprints for those tools.

4. HTTP/2 Prefaces

94 connections from 87 addresses began with the HTTP/2 connection preface, which nginx logs as:

PRI * HTTP/2.0

The full preface is PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n, followed by binary frames. A client that sends it on port 80 is testing for "h2c", HTTP/2 without TLS. Few public servers support it, but proxies that do have had request-smuggling bugs, so scanners keep a list. Most senders came once; the busiest were 66.132.224.89 (2), 66.132.172.32 (2), 66.132.195.192 (2).

6. A 17-Protocol Census

The lab ran a rolling packet capture (tcpdump, full snap length, 20 files of 10 MB) on port 80 and the Docker bridges. A ring that small holds about a day and a half of traffic, and the last of it was overwritten on 15 November when the VM was restarted and a large package download passed through the capture filter. The packets for 22 October to 15 November no longer exist, so for that period we have only what nginx wrote down. What remains is the nginx request log (request line, User-Agent, Content-Type and the complete request body) and the Apache log from inside the container, both shipped to Microsoft Sentinel as they were written. Sections 6 to 8 use a new capture.

7. Why nginx Never Saw It

None of these 125 probes appear in the nginx log, and none got an answer. The packets show why. This is the MongoDB probe from 45.79.115.59:

+  0.0000 s  scanner  -> honeypot S   
+  0.0000 s  honeypot -> scanner  AS  
+  0.1379 s  scanner  -> honeypot R   
+  2.7160 s  scanner  -> honeypot AP  58 bytes
+  2.7160 s  honeypot -> scanner  R

The scanner sends a SYN and our server answers SYN-ACK. Then the scanner's own machine sends a reset, 0.18 seconds later (median). The scanner builds its packets itself instead of using the operating system's TCP stack; the operating system sees a SYN-ACK for a connection it never opened and resets it. The scanner does not notice. Seconds later (0.6 to 174.4 seconds after the SYN in this capture) it sends its probe as if the connection were still open, and our server, which has already closed it, answers with a reset. All 125 census probes went this way.

So this census learned nothing about our server except that port 80 was open, and a web server log would never show that it happened. On a firewall or flow log it is visible: many short connections from the same small set of addresses, each reset by the client before any data.

9. Odds and Ends

Random methods. Three requests from three Google Cloud addresses used made-up four-letter methods, and got a normal page:

2026-10-28 03:02:58  34.140.181.137   OCHH / HTTP/1.1  -> 200, 3684 bytes
2026-11-04 02:21:32  35.210.196.80    INVI / HTTP/1.1  -> 200, 3684 bytes
2026-11-05 07:35:33  35.210.39.217    JMTX / HTTP/1.1  -> 200, 3684 bytes

Apache passes unknown methods to PHP, and a script that does not check $_SERVER['REQUEST_METHOD'] treats them like GET. Scanners use this to find servers where a WAF that filters GET and POST can be bypassed by sending something else.

WebLogic T3. Oracle WebLogic's T3 protocol starts with a version line. Exploits for WebLogic deserialisation bugs begin exactly like this:

2026-10-31 17:05:37  103.210.22.74    't3 12.1.2'
2026-11-04 23:46:07  165.154.11.225   't3 12.1.2'

2026-11-03 04:28:57  35.244.17.9      'SSH-2.0-probe'
2026-11-03 05:03:14  34.93.191.113    'SSH-2.0-probe'

Shell fragments. Seven "requests" were pieces of shell commands, such as sh+/tmp/…. They are most likely the remains of exploit requests that contained a raw line break, so nginx logged the part after it as a request of its own.

| where SyslogMessage startswith "php_http: "
| extend j = parse_json(substring(SyslogMessage, 10))
| extend Client = tostring(j.client), Req = tostring(j.request), Status = toint(j.status)
| where isempty(tostring(j.method)) and Status == 400
| extend B0 = toint(unicode_codepoints_from_string(substring(Req, 0, 1))[0])
| extend Kind = case(
    B0 == 22, "TLS",                       // 0x16, TLS handshake record
    Req startswith "PRI * HTTP/2", "HTTP/2 preface",
    Req startswith "Gh0st" or Req has "|'|'|", "RAT C2 probe",
    Req startswith "CONNECT " , "proxy CONNECT",
    B0 == 3, "TPKT (RDP/S7)",              // 0x03 0x00
    Req startswith "SSH-", "SSH banner",
    Req startswith "t3 ", "WebLogic T3",
    "other")
| summarize Count = count(), Sources = dcount(Client), First = min(TimeGenerated), Last = max(TimeGenerated) by Kind
| order by Count desc

For the census that never reaches the application, use flow logs. With Azure VNet flow logs in Traffic Analytics, look for sources whose inbound connections to one port are almost all short and data-less:

NTANetAnalytics
| where TimeGenerated > ago(1d)
| where FlowDirection == "Inbound" and DestPort == 80
| summarize Flows = sum(AllowedInFlows), BytesFromSrc = sum(BytesSrcToDest), Dests = dcount(DestIp) by SrcIp
| where Flows > 10 and BytesFromSrc / Flows < 200
| order by Flows desc

Column names in NTANetAnalytics vary a little between flow-log versions; check yours before using this.

12. Mitigation

  • Nothing here needs a fix on a web server, as long as the web server only speaks HTTP. nginx's 400 answer is the right one.
  • The same probes find the services that do need protecting. RDP, SQL Server, MongoDB, Redis, memcached, IPMI, Siemens S7, DNP3 and Niagara Fox should never be reachable from the internet. If a scanner like this one gets a real answer from any of them on your address space, it is in a public index within days. Check your own ranges with the same tools before someone else does.
  • Do not run unexpected services on port 80 or 443 to "hide" them. This census tried 17 protocols on the web port.
  • Use flow logs, not only application logs, to see scanning. Section 7 is invisible to nginx.
  • If you run malware analysis sandboxes or RAT test labs, make sure their controllers are not reachable from the internet. The RAT probes in section 5 exist to find exactly those.
