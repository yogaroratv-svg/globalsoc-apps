7 Million Fetches, 24 GB and 60,000+ HTTP 403s: How Our Honeypot's Payload Harvester Became a Web Crawler, and Why VirusTotal and AbuseIPDB Missed It

A "safe" payload harvester on our Cisco ASA honeypot fetched every URL it saw, including the info URLs scanners put in their User-Agent, then recursed into every page it downloaded. It logged 7,065,375 fetch events and filled a 30 GB disk in four days, while the same IP was relaying mail-credential checks for someone else. Then we checked our IP on VirusTotal, AbuseIPDB and ten blocklists. Full numbers, root causes, and tested detections for MDE + Sentinel and Splunk + CrowdStrike.

Key Sections: What Happened · How a Harvester Becomes a Crawler · What It Did to Other People · What the Reputation Feeds Said · Why Reputation Misses This · Detections · Lessons for Honeypot Builders · Evidence

Data: Cisco ASA/FTD honeypot on Azure, 29 October – 11 November 2026 (the same VM as the SSH tunnel, after-login and SSH password posts). Reputation lookups were made live on 27 November 2026, 13:41–15:10 AEDT. Part of my honeypot detection series. Org A runs Microsoft Defender for Endpoint with Microsoft Sentinel; queries marked Tested ran against this honeypot's MDE data. Org B runs Splunk with CrowdStrike Falcon; its queries were not run against this data.

1. What Happened

This one is about my own mistake. The honeypot had a "loot harvester": whenever an attacker's request contained a URL (a dropper link in a command injection, a wget in an SSH command), it downloaded that URL into quarantine so I could analyse the payload without running it. Sensible idea. Then it did this:

The disk filling up is how I found out: on 17 November the Azure agent couldn't write its status file ([Errno 28] No space left on device), Run Command stopped working, and the VM became unmanageable until I snapshotted the disk and analysed a copy on a separate forensic VM.

2. How a Harvester Becomes a Crawler

Flaw 1 It looked for URLs everywhere

For every HTTP request the honeypot concatenated the path, every header and the body, and extracted anything matching (https?|ftp|tftp)://…. Headers are where internet scanners announce themselves: User-Agent: Mozilla/5.0 (compatible; Infrawatch/1.0; +https://infrawat.ch/). So every scanner visit handed the harvester a URL to fetch. Flaw 2 It recursed into everything it downloaded

To follow two-stage droppers (a shell script that downloads an ELF), the harvester re-scanned any downloaded file that was text, a script, or smaller than 64 KB, and fetched every URL inside it. There was no depth limit, no visited-URL set (only "don't refetch the URL you came from"), and no domain restriction. A scanner's homepage links to GitHub; GitHub pages link to more GitHub, Atlassian, Font Awesome, Wikipedia. The crawl only stopped each time Python hit its recursion limit (1,000 frames), and restarted with the next scanner visit.

None of these scanners did anything malicious to me. They sent a polite GET / with an honest User-Agent, and my code turned their courtesy link into a four-day crawl.

Flaw 3 Everything else that made it worse

  • TLS verification off (ssl.CERT_NONE), so nothing failed safe.
  • Runs as root, writing to the root filesystem, with no quota and no free-space check.
  • 25 MB read cap per file: a 25 MB Apache snapshot ZIP from ci-builds.apache.org (asterix-server-…-binary-assembly.zip) was downloaded four times, and the 25.3 MB Noto Color Emoji font from fonts.gstatic.com sat in quarantine alongside it.
  • Same egress IP as the honeypot, so every fetch was attributable to the same address the SSH tunnel was abusing.

3. What It Did to Other People

Up to about 403,000 fetch attempts got past the recursion bug and went out to third-party sites over four days (some of those failed at DNS and never connected), from one Azure IP, with a Wget/1.21.2 (linux-gnu) User-Agent. The sites noticed even if the reputation feeds didn't: at least 60,341 requests were refused with HTTP 403 and at least 14,687 were rate-limited with HTTP 429. 226 fetches hit the honeypot itself, which then logged them as "attacks" from its own IP. From the outside this is indistinguishable from an aggressive scraper, and it ran in parallel with the SSH tunnel in the tunnel post, which relayed 42,239 connections, mostly mail-credential checks, through the same IP.

MDE saw it too, but summarised: it recorded 7,705 outbound network events from the honeypot process between 29 October and 4 November (7,163 unique connections, at most 3,428 events a day, peaking at 527 distinct hosts in one hour), against 161,806 completed downloads in the harvester's own log. My reading is that the sensor aggregates repeated connections from a very chatty process; either way, the pattern was there to alert on.

5. Why Reputation Misses This

  • Reputation is built from victims' sensors. AbuseIPDB scores rise when many people's fail2ban, honeypots and WAFs report an IP. Noisy behaviour (SSH guessing, port scanning) hits thousands of sensors a day, so 193.46.255[.]86 sits at 235,829 reports. The tunnel operators connected to exactly one SSH server, mine. Nobody else saw them, so nobody reported them.
  • The abuse was spread thin. The relayed mail checks touched each of 13,053 mail servers once or twice. No single mail admin sees a pattern; most never file a report. The one feed built for mail behaviour, Spamhaus CSS, is the one that listed us.
  • The victims of the crawl don't report to these feeds. GitHub, Atlassian and Font Awesome answered with 403s and 429s at their CDN edge and moved on. Rate limiting is their defence, not crowd-sourced reporting.
  • Cloud IPs are shared and recycled. An Azure address with a 2% score today may have been someone else's last month and will be someone else's next month. Feeds deliberately decay old reports, and VirusTotal's last analysis of my IP was a month old.
  • Scores track noise, not intent. A research scanner that sent me three honest GET / requests scores 100%. The operator that relayed 34,205 connections scores 0%. If you block on score, you block the census and admit the operator.

Reputation feeds are useful for one thing here: confirming that a noisy brute-forcer is noisy. They are the wrong tool for "is my own server being abused?" and for spotting the operator behind an access-broker chain. That question has to be answered from your own telemetry.

6. Detections

D1. A server-side script suddenly talks to hundreds of hosts

Org A Tested: 31 hours by KQL's dcount() estimate (30 by exact count), 29 October 22:00 – 2 November, peaking at 527 distinct hosts in one hour, all from /usr/bin/python3 /opt/cisco-honeypot/cisco_asa_honeypot.py. It also fired once on 18 November for mitmdump on another of my lab VMs: a legitimate proxy, which is exactly the kind of thing to allow-list.

// A1 (MDE): a server-side script/service suddenly talking to hundreds of distinct internet hosts
DeviceNetworkEvents
| where Timestamp > ago(30d)
| where RemoteIPType == "Public"
| where ActionType in ("ConnectionRequest", "ConnectionSuccess", "ConnectionFailed")   // outbound only; excludes InboundConnectionAccepted
| where InitiatingProcessFileName matches regex @"^(python|node|java|php|ruby|perl|curl|wget)"   // has_any would miss "python3.10"
| where InitiatingProcessCommandLine !has "WALinuxAgent"          // Azure agent; add your own known updaters
| summarize Conns = count(), Hosts = dcount(RemoteIP), Domains = dcount(RemoteUrl), Ports = make_set(RemotePort, 10)
          by DeviceName, InitiatingProcessFileName, InitiatingProcessCommandLine, bin(Timestamp, 1h)
| where Hosts >= 100
| order by Hosts desc

Org B

`comment("B1: Falcon - one process opening connections to 100+ distinct internet hosts per hour")`
event_simpleName=NetworkConnectIP4 event_platform=Lin
| where NOT (cidrmatch("10.0.0.0/8", RemoteAddressIP4) OR cidrmatch("172.16.0.0/12", RemoteAddressIP4) OR cidrmatch("192.168.0.0/16", RemoteAddressIP4) OR cidrmatch("127.0.0.0/8", RemoteAddressIP4))
| bin _time span=1h
| stats count as conns dc(RemoteAddressIP4) as hosts values(RemotePort_decimal) as ports by _time aid ComputerName ContextProcessId_decimal
| where hosts>=100
| join type=left aid ContextProcessId_decimal
    [ search event_simpleName=ProcessRollup2 event_platform=Lin | rename TargetProcessId_decimal as ContextProcessId_decimal | fields aid ContextProcessId_decimal FileName CommandLine UserName ]
| table _time ComputerName FileName CommandLine UserName conns hosts ports
`comment("B2: Falcon DNS - distinct domains resolved per process per hour (crawler shape)")`
event_simpleName=DnsRequest event_platform=Lin
| bin _time span=1h
| stats dc(DomainName) as domains count as lookups by _time aid ComputerName ContextProcessId_decimal
| where domains>=200

D2. An internal source collecting 403s and 429s from many sites

Other people's rate limiters are a free sensor. If your egress goes through a proxy or next-gen firewall that logs HTTP status codes, a source that suddenly collects hundreds of 403/429 responses across hundreds of sites is crawling or being used.

Org A (Sentinel, CEF from a proxy/firewall; parse-tested on my workspace, no matching traffic there)

// A2 (Sentinel, firewall/proxy CEF): one internal source collecting 403/429 answers from many sites = crawler/abuse
CommonSecurityLog
| where TimeGenerated > ago(1d)
| where isnotempty(RequestURL) and DeviceAction !in~ ("deny", "block")
| extend Status = coalesce(toint(column_ifexists("EventOutcome", "")),                       // some vendors put the HTTP code here
                         toint(extract(@"(?:^|;|\s)(?:status|cs\d|httpStatus)=(\d{3})\b", 1, AdditionalExtensions)))  // CEF key=value; adjust key to your vendor
| summarize Requests = count(), Sites = dcount(DestinationHostName),
            Http403 = countif(Status == 403), Http429 = countif(Status == 429)
          by SourceIP, bin(TimeGenerated, 1h)
| where Sites >= 200 or Http429 >= 50

Org B

`comment("B3: Splunk proxy / Zeek http - an internal host collecting 403/429 from many sites")`
index=network (sourcetype=zeek:http OR sourcetype=bluecoat:proxysg:access:syslog)
| eval status=coalesce(status_code, status, http_status), site=coalesce(url_domain, dest_host, cs_host)
| bin _time span=1h
| stats count as requests dc(site) as sites sum(eval(if(status=403,1,0))) as http403 sum(eval(if(status=429,1,0))) as http429 by _time src_ip
| where sites>=200 OR http403>=200 OR http429>=50

D3. Your own egress IPs in the feeds you already ingest

Reputation is a lagging, partial signal, but it is cheap to watch for your own addresses. Spamhaus CSS was the one listing this incident produced.

Org A

// A3 (Sentinel): your own egress IPs in the threat-intel feeds you already ingest (reputation as a lagging signal)
let MyEgress = dynamic(["192.0.2.1", "192.0.2.2"]);   // your public egress IPs (RFC 5737 examples)
ThreatIntelIndicators
| where TimeGenerated > ago(30d)
| extend Ip = tostring(ObservableValue)
| where Ip in (MyEgress)
| project TimeGenerated, Ip, SourceSystem, Confidence, Tags

Org B Run a scheduled search of your egress IPs against your threat-intel lookup (for example the ip_intel KV store in Splunk ES), and add a daily DNSBL check of your mail-capable egress IPs.

7. Lessons for Honeypot Builders

  • Extract URLs from the attack surface only: command arguments, request bodies, query strings. Never from User-Agent, Referer or Host.
  • Depth 1 by default, depth 2 only for scripts, with a visited set, a per-root fetch budget (for example 20) and a per-domain rate limit.
  • Never fetch your own IPs, private ranges or the cloud metadata address, and allow-list known scanner domains as "never fetch".
  • Quarantine to a separate disk with a quota, and stop harvesting below a free-space floor.
  • Fetch from a different egress (a NAT gateway or a separate harvesting VM) so that your harvesting and your honeypot don't share an IP, and so you can rate-limit egress at the network layer.
  • Alert on your own honeypot's outbound traffic. D1 would have caught this on the first evening.
