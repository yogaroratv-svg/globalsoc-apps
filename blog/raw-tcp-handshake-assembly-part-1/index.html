1. Understanding a Raw TCP Handshake — Explained Two Ways

Way 1: The Plain-English Analogy (Writing the Postal Envelope Yourself)

Normally, when a program wants to connect to our honeypot server at 20.248.231.206, it calls a high-level function like connect() (using SOCK_STREAM). When you do that, the Linux kernel acts like a secretary: it hides all the networking details from you, writes the 20-byte IPv4 routing label and the 20-byte TCP tracking label, sends the SYN packet, waits for SYN-ACK, and replies with ACK automatically.

When we open a Raw Socket (SOCK_RAW) with IP_HDRINCL (IP Header Included), we fire the secretary. We tell the Linux kernel: "Do not touch my packet. I am handing you a raw 40-byte array of numbers that already contains the 20-byte IPv4 header from 115.129.50.130 to 20.248.231.206 and the 20-byte TCP header. Put these exact 40 bytes directly onto the network wire."

Way 2: The Technical Reality (Why the Kernel Tries to Sabotage Your Raw Socket!)

When you send a raw TCP SYN packet from source port 57543 using SOCK_RAW, something surprising happens when the honeypot (`20.248.231.206`) replies with its SYN-ACK:

  1. The honeypot's SYN-ACK packet arrives at your machine (`115.129.50.130`) addressed to port 57543.
  2. A copy of that packet is delivered to your assembly program's raw socket, AND a copy is delivered to the Linux kernel's built-in TCP stack.
  3. Because you bypassed connect(), the Linux kernel checks its list of official TCP sockets, sees nothing registered on port 57543, and says: "Who sent me a SYN-ACK for port 57543? Nobody is listening here!"
  4. The Linux kernel immediately fires a TCP RST (Reset) packet back to 20.248.231.206, killing your connection before your assembly code can send the final ACK!

The Fix: Before running our assembly program, we add one temporary firewall rule telling Linux to drop any outgoing RST packets from our test port 57543:

sudo iptables -I OUTPUT -p tcp --tcp-flags RST RST --sport 57543 -j DROP

2. Byte-by-Byte Map of Our 40-Byte IPv4 + TCP Packet

Every raw TCP handshake packet without data is exactly 40 bytes long: the first 20 bytes (`Offsets 0–19`) are the IPv4 Header, and the next 20 bytes (`Offsets 20–39`) are the TCP Header.

Byte Offset Header Layer Field Name Exact Bytes in raw_tcp.s What Those Bytes Mean
0 – 1 IPv4 (20B) Version, IHL, TOS 0x45, 0x00 4 = IPv4, 5 = five 4-byte words (20 bytes total IPv4 header)
2 – 3 IPv4 (20B) Total Packet Length 0x00, 0x28 40 bytes total (0x28 = 20 IPv4 + 20 TCP)
4 – 9 IPv4 (20B) ID, Flags, TTL, Protocol 0x13, 0x37, 0x40, 0x00, 0x40, 0x06 Packet ID 0x1337, Don't Fragment, TTL = 64, Protocol = 6 (TCP)
10 – 11 IPv4 (20B) IPv4 Header Checksum 0x00, 0x00 Kernel fills IPv4 header checksum automatically even with IP_HDRINCL
12 – 15 IPv4 (20B) Source IP Address 115, 129, 50, 130 Your Client IP: 115.129.50.130 (0x73, 0x81, 0x32, 0x82)
16 – 19 IPv4 (20B) Destination IP Address 20, 248, 231, 206 Honeypot Public IP: 20.248.231.206 (0x14, 0xf8, 0xe7, 0xce)
20 – 21 TCP (20B) Source Port 0xe0, 0xc7 Port 57543 in Big-Endian network order
22 – 23 TCP (20B) Destination Port 0x1f, 0x90 Port 8080 (or 0x01, 0xbb for Port 443)
24 – 27 TCP (20B) Sequence Number (Seq) 0x00, 0x00, 0x00, 0x01 Starts at 1 in our SYN packet; becomes 2 in our ACK packet
28 – 31 TCP (20B) Acknowledgment Number (Ack) 0x00, 0x00, 0x00, 0x00 0 during SYN; filled with Server_Seq + 1 during Step 3 ACK
32 TCP (20B) Data Offset 0x50 Upper nibble 5 = five 4-byte words (20 bytes TCP header)
33 TCP (20B) TCP Control Flags 0x02 → 0x10 0x02 = SYN (Step 1), 0x12 = SYN-ACK (Step 2), 0x10 = ACK (Step 3)
34 – 39 TCP (20B) Window, Checksum, Urgent 0xff, 0xff, csum, 0x00, 0x00 Window = 65535; 16-bit TCP Checksum computed over Pseudo-Header + TCP

3. How Step 3 (`ACK`) Works in Assembly: Reading `Y` and Sending `Y + 1`

A TCP 3-way handshake is simply the two computers proving to each other that they can both send and receive numbers:

  1. Packet 1 (SYN — You → Honeypot): You (`115.129.50.130`) send a packet with TCP Flag 0x02 (SYN) and your starting Sequence Number Seq = 1.
  2. Packet 2 (SYN-ACK — Honeypot → You): The honeypot (`20.248.231.206`) replies with TCP Flag 0x12 (SYN + ACK). Inside that packet:
    • Its Acknowledgment Number (Offset 28) is 1 + 1 = 2 (proving it received your SYN).
    • Its Sequence Number (Offset 24) is a brand-new random 32-bit number chosen by the honeypot—let's call it Y.
  3. Packet 3 (ACK — You → Honeypot): Because Y is randomly chosen by the server every time, you cannot hardcode it! Your assembly program must read Y from byte offset 24 of the received SYN-ACK packet, add 1 to it (Y + 1), write that into your packet's Acknowledgment field (Offset 28), change your Sequence Number to 2, and change your TCP Flag from 0x02 (SYN) to 0x10 (ACK).

Why We Use bswap Before Adding 1 in x86_64 Assembly

Network packets store multi-byte numbers in Big-Endian order (most significant byte first), whereas Intel/AMD x86_64 CPUs do addition in Little-Endian order (least significant byte first). So in assembly, computing Y + 1 takes just 4 instructions:

mov eax, dword ptr [rcx + 4]          # 1. Read Server's 32-bit Sequence Number (Y) from TCP header + 4 (Offset 24)
bswap eax                             # 2. Flip bytes from Network Big-Endian to CPU Little-Endian
inc eax                               # 3. Add 1 (compute Y + 1)
bswap eax                             # 4. Flip bytes back to Network Big-Endian
mov dword ptr [rip + raw_pkt + 0x1C], eax  # 5. Store Y + 1 into our TCP Acknowledgment field (Offset 28 / 0x1C)

4. Complete Assembly Source Code (`raw_tcp.s`)

Here is the complete, self-contained x86_64 assembly program (view `raw_tcp.s` on GitHub) that performs the raw 3-way handshake between 115.129.50.130 and 20.248.231.206:

.intel_syntax noprefix
.global _start

.section .data
.align 4
one: .long 1
addr_len: .long 16

dst_addr:
    .word 2                         # AF_INET
    .byte 0x1f, 0x90                # Port 8080 (big-endian)
    .byte 20, 248, 231, 206         # Honeypot Public IP: 20.248.231.206
    .quad 0

raw_pkt:
    # --- 20-Byte IPv4 Header (Offsets 0x00..0x13) ---
    .byte 0x45                      # [0x00] IPv4, Header len = 20 bytes
    .byte 0x00                      # [0x01] TOS
    .byte 0x00, 0x28                # [0x02] Total Length = 40 bytes
    .byte 0x13, 0x37                # [0x04] ID = 0x1337
    .byte 0x40, 0x00                # [0x06] Dont Fragment
    .byte 0x40                      # [0x08] TTL = 64
    .byte 0x06                      # [0x09] Protocol = 6 (TCP)
    .byte 0x00, 0x00                # [0x0A] IP Checksum
    .byte 115, 129, 50, 130         # [0x0C] Source IP = 115.129.50.130 (Yogesh Client IP)
    .byte 20, 248, 231, 206         # [0x10] Dest IP   = 20.248.231.206 (Honeypot Public IP)

    # --- 20-Byte TCP Header (Offsets 0x14..0x27) ---
    .byte 0xe0, 0xc7                # [0x14] Source Port = 57543 (0xe0c7)
    .byte 0x1f, 0x90                # [0x16] Dest Port   = 8080  (0x1f90)
    .byte 0x00, 0x00, 0x00, 0x01    # [0x18] Sequence Number = 1
    .byte 0x00, 0x00, 0x00, 0x00    # [0x1C] ACK Number      = 0
    .byte 0x50                      # [0x20] Data Offset = 5 words (20 bytes)
    .byte 0x02                      # [0x21] TCP Flags   = 0x02 (SYN!)
    .byte 0xff, 0xff                # [0x22] Window Size = 65535
    .byte 0x00, 0x00                # [0x24] TCP Checksum (Computed by calc_tcp_csum)
    .byte 0x00, 0x00                # [0x26] Urgent Pointer = 0

pseudo_buf:
    .byte 115, 129, 50, 130         # [0x00] Source IP = 115.129.50.130
    .byte 20, 248, 231, 206         # [0x04] Dest IP   = 20.248.231.206
    .byte 0x00, 0x06                # [0x08] Zero + Protocol (6 = TCP)
    .byte 0x00, 0x14                # [0x0A] TCP Length = 20 bytes
    .space 20, 0                    # [0x0C..0x1F] Copy of 20-byte TCP header
