The Honeypot Detection Playbook: What Attacked My Server, and the Splunk and Sentinel Rules to Catch It

I ran a deliberately vulnerable PHP server on the internet and turned everything that hit it into detections. This is the hub: the kill-chain and ATT&CK coverage map, the data sources you need, and links to twelve posts with tested queries for Splunk + CrowdStrike Falcon and Microsoft Sentinel + Defender for Endpoint.

Key Sections: Why I Built This · How to Read the Series · Coverage Map · The Five Rules to Build First · Data You Need · The Posts

1. Why I Built This

I put a vulnerable PHP container on a public IP the day after a new PHP bug was disclosed, logged everything into Microsoft Sentinel, and watched. The first request arrived after 33 minutes. Over the next three and a half weeks it took 135,442 SSH password guesses, about 10,500 web requests from more than 1,100 addresses, and every flavour of exploit, credential hunt and scanner you'd expect, plus a few I didn't.

The traffic itself isn't the interesting part. What matters is what a defender should do about it. So each post in this series takes one kind of attack and walks through it the same way:

  • the attack step by step, with each step mapped to the kill chain and MITRE ATT&CK
  • a Pyramid of Pain table: which indicators are worth your time, and which ones the attacker changes overnight
  • detections for two organisations, from cheap web-layer rules up to behavioural endpoint rules
  • what to do when each rule fires, and the hardening that makes it not matter

2. How to Read the Series

Every detection is written twice:

  • Org A Splunk + CrowdStrike Falcon. Web logs come through the CIM Web data model or raw nginx, and endpoint data comes from Falcon Data Replicator events (ProcessRollup2, NetworkConnectIP4, DnsRequest). Correlation uses Enterprise Security risk-based alerting.
  • Org B Microsoft Sentinel + Defender for Endpoint. Web logs come through a WebAccess parser, and endpoint data comes from Defender XDR's Advanced Hunting tables (DeviceProcessEvents, DeviceNetworkEvents, DeviceFileEvents). Correlation uses scheduled analytics rules.

Every web-layer KQL query was run against the honeypot's real logs, and the counts in each post are what came back. The honeypot had no EDR on it, so the endpoint queries are written from the payloads the attackers sent, which tell you exactly what would have run. Treat their field names as a starting point for your environment.

4. The Five Rules to Build First

If you only build five rules from the whole series, build these. Each one sits near the top of the Pyramid of Pain, so it outlives any particular CVE:

  1. Web server or app runtime spawns a shell or downloader (RedTail E1). It catches almost every successful web RCE in the series, whatever the bug.
  2. SSH success after failures (SSH L3). It tested at zero results on the honeypot, and that's what you want: when it fires, it matters.
  3. A secret file was actually served (.env W2). It compares response size with the home page, which removed all 16 false positives a status-only rule would have raised.
  4. Exploit burst against a host, correlated with an endpoint hit (Spray C1). This turns daily noise into one incident with the story attached.
  5. Web tier egress on SSH, or to a raw IP on a high port (RedTail E2, React2Shell E2). Droppers and reverse shells both have to leave the box.

The Org B web parser used throughout the series. Swap the source for your own and keep the column names:

let WebAccess = Syslog
| where SyslogMessage startswith "php_http: "
| extend j = parse_json(substring(SyslogMessage, 10))
| project TimeGenerated, SrcIp = tostring(j.client), Method = tostring(j.method), Request = tostring(j.request),
          Url = tostring(j.uri), Status = toint(j.status), BytesOut = toint(j.bytes_out),
          UserAgent = tostring(j.user_agent), ContentType = tostring(j.content_type), Body = tostring(j.body);
