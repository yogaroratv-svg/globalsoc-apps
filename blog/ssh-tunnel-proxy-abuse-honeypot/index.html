42,239 Tunnelled Connections: How One SSH Login Turned Our Honeypot Into a Proxy for Mail Credential Checking and Ad Fraud

A decoy SSH account on our Cisco ASA honeypot was brute-forced, validated, handed to a proxy operator and used for 12 days as a SOCKS exit: 42,239 outbound connections to 33,123 IPs, 15,851 IMAP connections to 13,053 mail servers, SMTP, POP3 and ad exchanges. Full kill chain from Defender for Endpoint telemetry, and tested detections for MDE + Sentinel and Splunk + CrowdStrike.

Key Sections: What Happened · The Attack, Step by Step · How We Attributed It · Pyramid of Pain · Detections · When It Fires · Hardening · IOCs

Data window: 29 October – 11 November 2026, Cisco ASA/FTD SSL VPN honeypot on an Azure Ubuntu VM (OpenSSH, port 22 open to the internet). Part of my honeypot detection series. Org A runs Microsoft Defender for Endpoint with Microsoft Sentinel. Every Org A query marked Tested ran against this honeypot's real MDE data and the counts are what came back. Org B runs Splunk with CrowdStrike Falcon. Its queries use Falcon Event Search field names and the Splunk Add-on for Unix and Linux; they are written from the same behaviour and were not run against this data.

1. What Happened

The honeypot accepted any password for 40 decoy accounts and dropped every login into a fake Cisco ASA shell. The shell was the trap. What I hadn't blocked properly was SSH itself: an attacker doesn't need a shell to use an SSH server as a proxy. One decoy account, support, became a SOCKS exit node for 12 days.

The honeypot's own logs never saw any of this. My fake shell logged commands, the PAM module logged passwords, tcpdump captured ports 22/80/443/8443 with the payload encrypted. The tunnel lived entirely inside SSH channel requests that sshd at LogLevel VERBOSE does not log. Defender for Endpoint saw it because it records every outbound connection with its owning process, and the owning process was sshd: support.

2. The Attack, Step by Step

Recon Step 1: Port 22 found

The VM got its public IP on 29 October. The first SSH password attempts arrived the same evening (T1595.001 Active Scanning: Scanning IP Blocks).

Credential Access Step 2: A botnet guesses support

The first successful support login came from 109.160.32[.]200 at 21:30:10 UTC on 29 October. That /24 is the same wordlist-worker botnet I documented on the PHP honeypot in the SSH brute-force post: ten IPs in 109.160.32[.]0/24 each sent 1,196–1,197 passwords to this honeypot, in lockstep. support / support was the most common pair used for that account (22 times). T1110.001 Password Guessing, T1078.003 Valid Accounts: Local Accounts, T1021.004 Remote Services: SSH.

Validation Step 3: The access is re-checked by other workers

On 30 October the same credential was confirmed again from 109.160.32[.]165, 109.160.32[.]152, 109.160.32[.]35 and 2.57.122[.]76 (2.57.122[.]76 alone logged in nine times between 12:59 and 13:08, one a minute: a scripted liveness test), then 171.231.190[.]52. Two of them ran exactly one harmless command each and left: 109.160.32[.]165 ran uname -s -v -n -r -m and uname -m | awk '{printf $1}' 1.2 and 4.3 seconds after logging in at 11:38:48; 109.160.32[.]35 ran uname -m | awk '{printf $1}' 1.2 seconds after its 14:46:49 login. The rest ran nothing. That is what a credential pipeline looks like: guessers find a login, checkers confirm it still works, and only then does someone use it.

Hand-over Step 4: A different operator arrives

193.46.255[.]86 logged in as support at 17:10:51. It logged in as support 11 times across the whole 12 days, roughly once a day (31 Oct 17:31, 2 Nov 10:27, 3 Nov 11:02, 4 Nov 12:29, 5 Nov 16:04, 6 Nov 17:04, 8 Nov 04:21, 9 Nov 11:02, 10 Nov 12:30, 11 Nov 20:29 UTC), and never tunnelled anything itself: a monitor keeping an eye on an asset it was renting out (my inference from the pattern; I can't see who controls it). Twenty-six minutes after its first login, the proxy traffic started.

Command and Control Step 5: SSH dynamic port forwarding

At 17:36:13 208.69.78[.]9 logged in as support and, twenty seconds later, the sshd: support process started opening outbound TCP connections to the internet. An SSH client does this with ssh -D (a local SOCKS listener) or by sending raw direct-tcpip channel-open requests: the server makes the TCP connection and relays the bytes (T1090 Proxy, T1572 Protocol Tunneling). No shell or command is involved, so the ForceCommand trap never mattered.

Three operator IPs ran the tunnel in sequence. Each session started minutes after the previous one ended:

Actions on Objectives Step 6: What went through the tunnel

MDE resolves many destinations to the hostname the client asked for, which shows what the proxy was sold for:

  • Mail credential checking (T1110.004 Credential Stuffing against third parties): 15,851 IMAP connections to 13,053 distinct mail servers and 613 POP3 connections to 590. Large providers (imap.comcast.net 865, outlook.office365.com 454, login.live.com 210, imap.gmail.com) and thousands of small business and ISP mail hosts, a large share of them Australian .com.au and .org.au domains. One or two connections per server, spread across the list: a combo-list checker testing email:password pairs against each address's own mail server. I am not publishing the small-business hostnames; they are victims.
  • SMTP: 8,236 connections to 6,628 servers on 25/465/587, including smtp.office365.com (104). Consistent with validating SMTP AUTH or sending through compromised mailboxes. The payloads were inside the encrypted SSH channel, so I can't tell which.
  • Ad and analytics traffic: real-time bidding and sync endpoints (ib.adnxs.com 299, exchange.kueezrtb.com 171, s.amazon-adsystem.com 153, eb2.3lift.com, cm.adform.net, user-sync.fwmrm.net, dt.adsafeprotected.com, ad.doubleclick.net, id5-sync.com), plus property and news sites. Browser-shaped traffic from a datacentre IP to ad exchanges is how residential/datacentre proxy pools are monetised for ad fraud and traffic resale.
  • Proxy self-checks: my packet capture (which only covered 80/443) caught the clear-text checks a proxy customer runs before using an exit: GET /json/?fields=status,message,country,countryCode,query,isp to ip-api.com, GET /ip.shtml, and GET /internals/api/ip?<nonce> to 37.27.142.x.

Impact What it means for the owner

For 12 days my Azure IP was the visible source of credential-checking traffic against more than thirteen thousand mail servers and of ad-exchange traffic. Any of those operators can file an abuse report against the IP, and the mail checking will be in their logs as my address. Proxy abuse costs the victim almost nothing in CPU, which is exactly why it goes unnoticed: the B-series VM's bill did not move.

Reputation feeds didn't notice either. On 27 November, two weeks after the last tunnelled connection, the honeypot's public IP 20.5.248[.]133 had no detections on VirusTotal, Malwarebytes returned "unknown" (no threat intelligence), and DNS lookups at 13:41 AEDT found it on none of SpamCop, Barracuda, SORBS, CBL, PSBL, UCEPROTECT levels 1 and 2, blocklist.de or s5h. Twelve days of IMAP/SMTP checking against more than thirteen thousand mail servers left almost no reputation trace, because the traffic was spread thinly: one or two connections per server. Don't treat a clean reputation for your own egress IP as evidence that nothing is wrong; the detections in section 5 are on your side of the wire for a reason.

3. How We Attributed It (MDE)

Linux sshd forks one process per connection: a privileged monitor (sshd: support [priv]), and a child that runs as the user (sshd: support). The tunnel connections belong to the child. MDE's DeviceLogonEvents row for the same login carries a LogonId equal to the monitor's PID, which is the child's parent PID. So:

DeviceNetworkEvents.InitiatingProcessParentId  ==  DeviceLogonEvents.LogonId

That one join gives you, for every tunnelled connection, the account, the source IP of the SSH login, and when the login happened. It is query A2 below. Without it you only know "sshd talked to 33,000 IPs".

Two counting notes for anyone reproducing this. MDE writes separate ConnectionRequest, ConnectionSuccess and ConnectionFailed rows for one TCP connection, so count unique (InitiatingProcessId, LocalPort, RemoteIP, RemotePort) tuples, not rows. And KQL dcount() is an estimate (HyperLogLog, about 1–2% off at these sizes): the Tested figures below are what the queries returned; the tables above are exact counts from the exported raw rows.

5. Detections

D1. sshd is the process talking to the internet (T1090, T1572)

Org A Tested: 12 tunnel sessions returned. The top one was support, 65,414 events (Conns) to 31,171 IPs (dcount) on ports 993, 143, 443, 465, 587, 25, 110, 995, 80, 853, 5228 and 3629.

// A1: sshd itself opening outbound connections to the internet = SSH port forwarding (direct-tcpip)
DeviceNetworkEvents
| where Timestamp > ago(30d)
| where InitiatingProcessFileName == "sshd"
| where InitiatingProcessCommandLine startswith "\"sshd: "   // per-user session process, not the listener
| where RemoteIPType == "Public"
| summarize Conns = count(), Dsts = dcount(RemoteIP), Ports = make_set(RemotePort, 20),
            First = min(Timestamp), Last = max(Timestamp)
          by DeviceName, Account = InitiatingProcessAccountName,
             SessionPid = InitiatingProcessId, LogonId = tostring(InitiatingProcessParentId)
| where Dsts >= 20

Org B Falcon records NetworkConnectIP4 with the owning process in ContextProcessId. Join it to the ProcessRollup2 of sshd:

`comment("B1: Falcon - outbound connections whose owning process is sshd")`
event_simpleName=NetworkConnectIP4
| where NOT (cidrmatch("10.0.0.0/8", RemoteAddressIP4) OR cidrmatch("172.16.0.0/12", RemoteAddressIP4) OR cidrmatch("192.168.0.0/16", RemoteAddressIP4) OR cidrmatch("127.0.0.0/8", RemoteAddressIP4))
| join type=inner aid ContextProcessId_decimal
    [ search event_simpleName=ProcessRollup2 FileName=sshd
      | rename TargetProcessId_decimal as ContextProcessId_decimal
      | fields aid ContextProcessId_decimal UserName CommandLine ParentProcessId_decimal ]
| stats count as conns dc(RemoteAddressIP4) as dsts values(RemotePort_decimal) as ports
        min(_time) as first max(_time) as last by aid ComputerName UserName ContextProcessId_decimal ParentProcessId_decimal
| where dsts>=20
| convert ctime(first) ctime(last)

Legitimate SSH servers make almost no outbound connections from the per-user sshd: bastion hosts that people use with -L/-D are the exception, and you can list them. Tune with an allow-list of jump hosts and keep Dsts >= 20.

D2. Attribute each tunnel to the login that opened it

Org A Tested: 286 attributed sessions; the top four rows are exactly the operator table in section 2 (208.69.78[.]179 219.6 h, 66.163.116[.]25 52.0 h, 208.69.78[.]9 19.4 h, 212.87.213[.]69 9.6 h).

// A2: attribute every tunnel to the SSH logon that opened it (LogonId == parent pid of the session sshd)
let Tunnels = DeviceNetworkEvents
    | where Timestamp > ago(30d) and InitiatingProcessFileName == "sshd" and RemoteIPType == "Public"
    | where InitiatingProcessCommandLine startswith "\"sshd: "
    | summarize Conns = count(), Dsts = dcount(RemoteIP), Ports = make_set(RemotePort, 15),
                First = min(Timestamp), Last = max(Timestamp)
              by DeviceId, LogonId = tostring(InitiatingProcessParentId), Account = InitiatingProcessAccountName;
DeviceLogonEvents
| where Timestamp > ago(30d) and ActionType == "LogonSuccess" and LogonType == "Network"
| project DeviceId, DeviceName, LogonId = tostring(LogonId), RemoteIP, LogonTime = Timestamp
| join kind=inner Tunnels on DeviceId, LogonId
| project LogonTime, DeviceName, Account, RemoteIP, Conns, Dsts, Ports, First, Last,
          SessionHours = round((Last - First) / 1h, 1)
| order by Conns desc

Org B In Falcon the SSH login is a UserLogon event whose ContextProcessId is the sshd monitor. The B1 search already carries ParentProcessId_decimal; join it to UserLogon on that ID to get RemoteAddressIP4 of the login.

D3. Mail-protocol fan-out from a server (T1110.004 against third parties)

Org A Tested (30-day window): 253 hours in which the honeypot spoke IMAP/POP3/SMTP to 50 or more mail servers. In all 253, sshd was the only initiating process.

// A3: a server that suddenly talks IMAP/POP3/SMTP to hundreds of mail servers
DeviceNetworkEvents
| where Timestamp > ago(1d)
| where RemotePort in (25, 465, 587, 110, 995, 143, 993) and RemoteIPType == "Public"
| summarize MailServers = dcount(RemoteIP), Conns = count(),
            Procs = make_set(InitiatingProcessFileName, 5), Samples = make_set(RemoteUrl, 10)
          by DeviceName, bin(Timestamp, 1h)
| where MailServers >= 50

Org A Without MDE on the VM, Sentinel's Traffic Analytics table gives the same signal per source IP (not run here: flow logs only covered a different lab VNet):

// A4 (Sentinel): the same idea from Azure network flow data when there is no EDR on the box
NTANetAnalytics
| where TimeGenerated > ago(1d)
| where SubType == "FlowLog" and FlowDirection in ("O", "Outbound") and DestPort in (25, 465, 587, 110, 995, 143, 993)
| mv-expand DestIp = split(DestPublicIps, " ")          // external destinations live in DestPublicIps, not DestIp
| extend DestIp = tostring(split(DestIp, "|")[0])
| where isnotempty(DestIp)
| summarize MailServers = dcount(DestIp), Flows = count() by SrcIp, bin(TimeGenerated, 1h)
| where MailServers >= 50

Org B

`comment("B2: Falcon - server suddenly speaking IMAP/POP3/SMTP to many mail servers")`
event_simpleName=NetworkConnectIP4 RemotePort_decimal IN (25,465,587,110,995,143,993)
| bin _time span=1h
| stats dc(RemoteAddressIP4) as mail_servers count as conns values(ContextBaseFileName) as procs by _time aid ComputerName
| where mail_servers>=50
`comment("B3: Splunk + Zeek / firewall - same thing without EDR")`
index=network (sourcetype=zeek:conn OR sourcetype=pan:traffic) dest_port IN (25,465,587,110,995,143,993)
| where (cidrmatch("10.0.0.0/8", src_ip) OR cidrmatch("172.16.0.0/12", src_ip) OR cidrmatch("192.168.0.0/16", src_ip))
    AND NOT (cidrmatch("10.0.0.0/8", dest_ip) OR cidrmatch("172.16.0.0/12", dest_ip) OR cidrmatch("192.168.0.0/16", dest_ip))
| bin _time span=1h
| stats dc(dest_ip) as mail_servers count as conns by _time src_ip
| where mail_servers>=50

Servers that legitimately do this are your mail relays and mail-archiving appliances. Everything else, especially a Linux VM in a cloud subnet, should never open 50 IMAP sessions an hour.

D4. One SSH session that lasts for days

Org A Tested: 6 sessions of 12 hours or more, all support; the longest was 219.6 hours.

// A5: one SSH logon that lasts for days (a proxy session, not an admin)
DeviceLogonEvents
| where Timestamp > ago(30d) and ActionType == "LogonSuccess" and LogonType == "Network"
| project DeviceId, DeviceName, LogonId = tostring(LogonId), AccountName, RemoteIP, LogonTime = Timestamp
| join kind=inner (
    DeviceNetworkEvents
    | where Timestamp > ago(30d) and InitiatingProcessFileName == "sshd"
    | summarize LastSeen = max(Timestamp), Conns = count() by DeviceId, LogonId = tostring(InitiatingProcessParentId)
  ) on DeviceId, LogonId
| extend Hours = round((LastSeen - LogonTime) / 1h, 1)
| where Hours >= 12
| project DeviceName, AccountName, RemoteIP, LogonTime, LastSeen, Hours, Conns

Org B

`comment("B5: Splunk linux_secure - session that stays open for 12h+ (Accepted ... -> Disconnected/closed)")`
index=linux sourcetype=linux_secure process=sshd ("Accepted" OR "session closed")
| rex "sshd\[(?<pid>\d+)\]"
| rex "Accepted \S+ for (?<user>\S+) from (?<src>\S+)"
| stats min(_time) as start max(_time) as end values(user) as user values(src) as src by host pid
| eval hours=round((end-start)/3600,1)
| where hours>=12

D5. Make sshd log the forwarding itself

At LogLevel VERBOSE OpenSSH logs logins, keys and disconnects, but not channel requests. At LogLevel DEBUG1 every direct-tcpip request is logged as server_request_direct_tcpip: originator <ip> port <port>, target <host> port <port>. DEBUG1 is chatty, so turn it on for exposed hosts only, or use EDR network telemetry instead.

Org A

// A6 (Sentinel, Syslog): sshd only logs forwarding at LogLevel DEBUG1 - "server_request_direct_tcpip"
Syslog
| where ProcessName == "sshd" and SyslogMessage has "server_request_direct_tcpip"
// OpenSSH serverloop.c: "server_request_direct_tcpip: originator <ip> port <p>, target <host> port <p>"
| extend Target = extract(@"target ([^ ]+) port (\d+)", 1, SyslogMessage),
         TPort = toint(extract(@"target [^ ]+ port (\d+)", 1, SyslogMessage))
| summarize Requests = count(), Targets = dcount(Target), Ports = make_set(TPort, 20) by Computer, bin(TimeGenerated, 1h)
| where Targets >= 20

Org B

`comment("B4: Splunk linux_secure - sshd forwarding requests (needs LogLevel DEBUG1) and long sessions")`
index=linux sourcetype=linux_secure process=sshd "server_request_direct_tcpip"
| rex "target (?<target>\S+) port (?<tport>\d+)"
| bin _time span=1h
| stats count as requests dc(target) as targets values(tport) as ports by _time host
| where targets>=20

6. When It Fires

  • Kill the session first, then the account. Org A Isolate the device from the MDE device page, or run pkill -KILL -u <user> sshd through Live Response. Org B Network-contain the host in Falcon, or kill the sshd PID from Real Time Response.
  • Find every account it used. Run D2 for the last 30 days. Each attributed row is a separate login; rotate or lock each account, not just the one that alerted.
  • Work out the blast radius for others. The destinations in D1 are other people's servers. If mail ports are in the list, expect abuse reports, and check whether your egress IP is now on mail blocklists.
  • Look for the shell side too. On a real server the same login also gets a real shell. Check the session's process tree (DeviceProcessEvents / ProcessRollup2 with the same parent) for persistence: authorized_keys writes, cron, new users.

7. Hardening

  • The root cause here: my config said Match User !labadmin,!root followed by ForceCommand and AllowTcpForwarding no. In OpenSSH patterns a negated entry can only exclude; a list made only of negations never matches anyone (ssh_config(5), PATTERNS). So the whole block, forwarding restriction and ForceCommand included, applied to nobody, and OpenSSH's default AllowTcpForwarding yes stayed in force. MDE agrees: the ForceCommand target ran 0 times while the decoy login shell ran 2,479 times. The correct line is Match User *,!labadmin,!root.
  • Better still, set AllowTcpForwarding no, AllowStreamLocalForwarding no, PermitTunnel no and PermitOpen none in the global section, and re-enable per jump host with a positive Match. Verify the effective value per user with sshd -T -C user=support,host=x,addr=192.0.2.1 | grep -i forward. Test what sshd enforces, not the file you edited.
  • Egress filtering: a Linux server has no business opening IMAP, POP3 or SMTP to the internet. Deny 25/110/143/465/587/993/995 outbound at the NSG/firewall for everything except mail relays.
  • No password authentication on internet-facing SSH. The whole chain started with a guessed password.
  • Session limits: ClientAliveInterval plus a maximum session age enforced by your PAM/session tooling, so a stolen login can't live for nine days.
