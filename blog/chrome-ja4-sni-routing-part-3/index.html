1. Why We Built Two Different Assembly Packets: "Weird" vs. "Chrome"

In Part 2, we built a minimal 117-byte TLS 1.3 ClientHello (`raw_tcp_tls_ja4.s`), and then in `raw_chrome.s` we expanded it to 247 bytes to mimic Google Chrome. Comparing those two packets side-by-side shows why JA4 is so important for both senders and defenders:

Feature Packet A: Stripped-Down Assembly (raw_tcp_tls_ja4.s) Packet B: Chrome-Disguised Assembly (raw_chrome.s)
Total Packet Size 157 bytes (40B IP/TCP + 117B TLS) 287 bytes (40B IP/TCP + 247B TLS)
JA4 Fingerprint t13n010400_0f2cb44170f4_f86e416269f0 t13d1514h2_8daaf6152771_02713d6af862
SNI Extension (0x0000) None (n) globalsoc.com.au (d = domain present)
Cipher Suites Count 01 (Only 0x1301) 15 (All 15 standard Chrome TLS 1.3 + 1.2 ciphers)
Extensions & ALPN 04 extensions, 00 (No ALPN) 14 extensions, h2 (HTTP/2 ALPN)
How a SOC Defender Sees It Immediate Red Flag! No normal browser on an employee laptop ever connects with 1 cipher, 4 extensions, and no domain name. Blends In Completely! To a JA4 firewall rule, this raw assembly binary looks identical to Google Chrome.

2. How Does `globalsoc.com.au` Come Into the Picture When Sending from `115.129.50.130` to `20.248.231.206`?

This is one of the most confusing concepts in networking until you see it explained two ways: how can we send a packet from our IP `115.129.50.130` to the honeypot IP `20.248.231.206`, write `"globalsoc.com.au"` inside the packet, and still have it land on our honeypot without ever touching the real `globalsoc.com.au` server?

Way 1: The Postal Envelope vs. The Letter Inside

Think of your 287-byte network packet as a physical paper letter inside a stamped envelope:

  1. The Outside of the Envelope (Bytes 12–19: IPv4 Header):
    • From: 115.129.50.130 (Your IP)
    • Deliver To: 20.248.231.206 (Our Azure Honeypot IP)
    The postal trucks (Internet Routers) ONLY read the IP address on the outside of the envelope. They never open the envelope! So the packet is guaranteed to be delivered straight to our honeypot at 20.248.231.206.
  2. The Letter Inside the Envelope (TLS Extension `0x0000` SNI):
    • Inside the letter, we wrote the plain-text words: "Hello, I am here to visit globalsoc.com.au" (or "skyscanner.com", or "bravofly.com").
    Why does that field exist? Because a single web server IP often hosts 50 different websites, so a normal browser writes the website name inside the letter to tell the server which website's certificate to hand back.

The Trick: Because we built the packet ourselves in assembly (`raw_chrome.s`), nobody stops us from addressing the outside of the envelope to 20.248.231.206 while writing a completely different domain name (like globalsoc.com.au) inside the TLS SNI field! Our honeypot at 20.248.231.206 gets the traffic, but a basic security monitor reading the SNI field thinks you are visiting globalsoc.com.au!

Way 2: The Exact Byte Layout Inside `raw_chrome.s`

Here is how those two separate layers sit inside the same 287-byte packet in `raw_chrome.s`:

  • Layer 3 (Bytes 12–19 — Where the packet actually goes): 
    .byte 115, 129, 50, 130         # [Offset 0x0C] Source IP      = 115.129.50.130 (You)
.byte 20, 248, 231, 206         # [Offset 0x10] Destination IP = 20.248.231.206 (Honeypot)
  • Layer 7 (Inside the TLS `ClientHello` — What the SNI extension claims): 
    # Extension 0x0000 (Server Name Indication = "globalsoc.com.au")
.byte 0x00, 0x00                # Extension Type: 0x0000 (server_name)
.byte 0x00, 0x15                # Extension Length: 21 bytes (0x0015)
.byte 0x00, 0x13                # Server Name List Length: 19 bytes (0x0013)
.byte 0x00                      # Server Name Type: 0x00 (DNS Hostname)
.byte 0x00, 0x10                # Hostname Length: 16 bytes ("globalsoc.com.au")
.ascii "globalsoc.com.au"       # The 16 ASCII bytes read by firewalls & JA4 ("d")

3. Auditing 19,613 Real TLS Handshakes on Our Honeypot: Who Is Spoofing SNI Right Now?

We audited all 19,613 TLS handshakes (`tls_attacks.jsonl`) and 30,782 HTTP requests (`http_attacks.jsonl`) captured on our live Azure honeypot (`20.248.231.206`). Here are the three real-world attacker techniques we caught:

Finding 1: The "Bravofly" SNI Impersonator (`50.236.138.77`)

Out of 19,613 external TLS connections, one attacker IP (50.236.138.77) connected to our raw Azure IP 20.248.231.206 and injected a real company's domain name into the TLS ClientHello SNI field:

  • Attacker IP: 50.236.138.77 → Honeypot IP: 20.248.231.206
  • Injected TLS SNI: bravofly.com (a major European flight booking website)
  • Captured JA4: t13d131000_f57a46bbacb6_a089bac06eae (Notice the d at character 4!)

Why did they do this? Attackers scan cloud IP ranges (like Azure and AWS) injecting popular domains like bravofly.com into the SNI field to hunt for forgotten origin servers or dangling DNS records (Subdomain Takeover / Virtual-Host hunting), or to make their outbound scanning traffic look like harmless travel-booking traffic to their local firewall.

Finding 2: How JA4's 4th Character (`i`) Caught 18,240+ Automated Scanner Bots

Over 18,240 TLS attacks (from 20.169.33.201, 94.102.49.190, 184.105.247.252, 45.138.12.51, and 138.197.176.235) tried to look like normal web clients by filling in the SNI field—but their scripts automatically copied our raw IP address ("20.248.231.206") into the DNS hostname slot!

  • According to internet standards (RFC 6066), a real web browser (Chrome, Edge, Safari, Firefox) will never put a raw IP address inside the SNI hostname extension.
  • When our honeypot's JA4 engine sees an IP address inside the SNI field instead of a domain name, it sets the 4th character of JA4 to i (IP literal) instead of d (Domain): t13i181100_... and t12i520900_....
  • Defensive Takeaway: In any SOC, a single filter rule matching t13i* or t12i* catches lazy automated IP scanners with zero false positives!

Finding 3: HTTP Proxy & Cloud Metadata Fronting (`http_attacks.jsonl`)

Once the TCP/TLS connection opened, several attackers sent HTTP requests with external domains in the request line to test if our server (`20.248.231.206`) could be tricked into forwarding their traffic (Open Proxy / SSRF):
